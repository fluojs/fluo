## Scope and selected versions

[Issue #3700](https://github.com/fluojs/fluo/issues/3700) updates two separate install graphs for nine public upstream advisories observed on 2026-09-06. The original 15 Dependabot alerts count the six shared advisories once per lockfile: nine distinct advisories, not 15 distinct defects. This is dependency maintenance, not a claim that every Fluo deployment exposes an exploitable request path.

| Dependency | Root workspace | Isolated HTTP benchmark | Classification |
| --- | --- | --- | --- |
| `fast-uri` | Major-3 override `3.1.7`; locks `3.1.7` and `4.1.4` | Major-3 override `3.1.7`; locks `3.1.7` and `4.1.4` | Transitive Fastify schema/serialization dependency |
| `fastify` | Public adapter dependency `^5.12.3`, lock `5.12.3` | Direct dependency `^5.12.3`, override and lock `5.12.3` | HTTP runtime |
| `qs` | Override and lock `6.16.0` | Not present in the isolated external lockfile | Transitive Express dependency |
| `browserslist` | Lock `4.28.9` | Not present in the isolated external lockfile | Development/build tooling, not HTTP request routing |

The advisory repair floors are `fast-uri 3.1.6`, `fastify 5.12.1`, `qs 6.16.0`, and `browserslist 4.28.7`. The selected releases include later compatible fixes available at implementation time. Ajv retains its major-3 URI parser, while the updated Fastify compiler/serializer dependencies require major 4. The override is scoped to `fast-uri@3` so it cannot force major 3 into a dependency requiring `^4.0.0`. Other lockfile movements belong to these dependencies' resolution closures, including Fastify's upstream `fast-json-stringify` 7 dependency.

Both lockfiles are generated by pnpm `10.4.1`. The root graph uses exact overrides for `fast-uri@3` and `qs` so an old transitive pin cannot preserve the affected versions. Browserslist's existing build-time ranges permit the patched version, so its transitive lock is refreshed without adding a runtime dependency or another override. The benchmark retains a Fastify override because its NestJS adapter has its own exact Fastify dependency; changing only the benchmark's direct dependency would leave that nested copy unresolved.

The benchmark's `link:../../../packages/*` dependencies load the current worktree's built Fluo packages, whose dependencies still resolve from the root workspace. Thus the isolated external lockfile does not describe the whole running benchmark. Both graphs must be installed and verified; neither is a published consumer install.

A fresh audit also identified [GHSA-c83g-rgw3-j3cx](https://github.com/advisories/GHSA-c83g-rgw3-j3cx) in Browserslist; the same update removes it. Audit services evolve independently of these nine advisories. Report additional findings separately rather than dismissing alerts or claiming that a scoped repair means an all-dependency audit is clean.

Compatibility evidence belongs to the existing Fastify/Express adapter suites, HTTP routing and connection-identity suites, Node request parsing, and validation suites. They preserve native-route handoff and fallback, duplicate query keys and decoding, body materialization, explicit proxy trust, and DTO validation. The governing behavior remains the [HTTP Runtime Contract](../architecture/http-runtime.md) and the adapter package READMEs.

The patched Fastify line also enforces RFC 10008: `QUERY` requires request content and a matching `Content-Type`. A bodyless or untyped `QUERY` now receives HTTP `400` before Fluo dispatch; do not use it as an empty `GET` substitute. Send a body such as `{"term":"fluo"}` with `Content-Type: application/json`. The native-fallback fixture now uses that valid request and asserts the delivered body as well as method, route, and status; it does not bypass upstream validation or downgrade Fastify to retain acceptance of malformed requests. Other adapters' acceptance of malformed input is not a portability guarantee.

## Published consumer graph

The root `pnpm.overrides` and both repository lockfiles are private installation policy. They are not inherited when npm or pnpm installs a published `@fluojs/*` dependency.

- **Fastify:** `@fluojs/platform-fastify -> fastify -> @fastify/ajv-compiler -> ajv -> fast-uri`. Fastify also reaches `fast-uri` through its compiler and `fast-json-stringify`/`json-schema-ref-resolver`. The public adapter now requires `fastify ^5.12.3`, so the release carrying this manifest cannot satisfy that dependency with `5.8.5`. It does not guarantee a patched nested major-3 `fast-uri`: Ajv's `^3.0.1` still permits an older consumer lock. The fresh packed npm consumer resolves Ajv to `fast-uri 3.1.7` and `@fastify/ajv-compiler 4.0.6` / `fast-json-stringify 7.0.1` to `fast-uri 4.1.4` through their `^4.0.0` ranges. These are distinct supported major lines, not duplicate vulnerable resolutions.
- **Express:** `@fluojs/platform-express -> express -> qs`, and `express -> body-parser -> qs`. The adapter keeps `express ^5.1.0`; even Express `5.2.1` permits `qs ^6.14.0`. Raising the Express floor would not impose `qs 6.16.0`, and adding an unused direct `qs` dependency to Fluo would not constrain every nested copy. Consumers must refresh or override that transitive resolution themselves.
- **Validation:** `@fluojs/validation` depends on `validator` and the Standard Schema contract, not Ajv or `fast-uri`. The Fastify schema dependency must not be attributed to Fluo DTO validation.
- **Build tools:** the repository's `@babel/core -> @babel/helper-compilation-targets -> browserslist` path is development/build work. Consumers using Babel through their build tools or the `@fluojs/vite` / `@fluojs/testing` peer surface should update their own build graph; this does not justify bumping unrelated public runtime packages.

Only `@fluojs/platform-fastify` receives a patch Changeset for the backward-compatible public dependency-floor repair. The Express manifest and Fluo runtime code do not change. Private root/benchmark and build-only lockfile updates do not require unrelated public package bumps. Versions and changelogs are released only by the canonical Changesets workflow.

## Consumer lockfile update

After the release carrying this change is published, upgrade `@fluojs/platform-fastify` to that release. Keep Node.js in the adapter's documented `>=24.0.0 <27` range. Refresh transitive locks in each application, image build, and independently installed workspace; upgrading Fluo's repository lock does not modify them.

For npm applications, update and inspect from the application root:

```bash
npm update @fluojs/platform-fastify fast-uri qs
npm ls fastify fast-uri qs browserslist --all
npm audit
```

For pnpm applications:

```bash
pnpm update @fluojs/platform-fastify
pnpm update fast-uri qs --depth Infinity
pnpm why fastify fast-uri qs browserslist
pnpm audit
```

Require every relevant installed copy to be at least the advisory repair floors above, with the new adapter's Fastify copy satisfying `^5.12.3`. Also refresh Browserslist when it exists in the application's build graph. Review and replace obsolete application pins, resolutions, or overrides that prevent those updates; do not downgrade a newer patched version.

If upstream constraints or an existing lock still retain affected transitive versions, an application receiving these packages only transitively can set npm root policy:

```json
{
  "overrides": {
    "fast-uri@3": "^3.1.7",
    "qs": "^6.16.0"
  }
}
```

For pnpm `10.4.1`, put the same entries under the application root's `pnpm.overrides`. Keep the URI override scoped to major 3; do not replace a required major-4 copy with major 3. Applications that directly depend on either package must align their direct manifest range too. Reinstall to regenerate the application lockfile, inspect **all** nested versions, run adapter/native-middleware/schema tests, and commit the reviewed lockfile before rebuilding and redeploying. A fresh install alone is not a permanent guarantee against an old compatible lock returning.

## Maintainer reproduction

Use Node 24 and pnpm `10.4.1`:

```bash
pnpm install --frozen-lockfile
pnpm audit
pnpm why fast-uri fastify qs browserslist
pnpm -r why fast-uri fastify qs browserslist
pnpm --dir tooling/benchmarks/http-comparison --ignore-workspace install --frozen-lockfile
pnpm --dir tooling/benchmarks/http-comparison --ignore-workspace audit
pnpm --dir tooling/benchmarks/http-comparison --ignore-workspace why fast-uri fastify
```

Build the affected workspace dependency closures before adapter tests and benchmark compilation. Run the Fastify/Express suites plus HTTP routing, connection identity, query/body parsing, and validation coverage, and exercise built adapters over real HTTP. Verify the isolated benchmark's `typecheck`, `build:fluo`, `build:fluo:bun`, and `build:nestjs`; throughput measurements are not required for this maintenance change.

For published-graph evidence, pack the built local adapters and their workspace production dependencies with pnpm, install those tarballs in an empty npm consumer without root overrides, and inspect its lockfile and `npm ls --all`. This checks the actual package manifests after `workspace:^` rewriting, rather than confusing a linked worktree install with npm consumer resolution. The root `build`, `typecheck`, `lint`, and `test` gates remain required in lead verification, together with `pnpm verify:platform-consistency-governance` and the stable `verify:changeset-release-lane` gate.
