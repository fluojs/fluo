# 1권 — FluoBlog: 처음 만드는 운영 가능한 서비스

[시리즈 소개](../README.ko.md) · [전체 목차](./toc.ko.md)

개발 경험을 글로 공유하려고 시작한 작은 블로그가 이 권의 제품이다. 처음에는 게시글 하나를 반환하면 충분하다. 글을 고치고 발행하기 시작하면 상태와 권한이 필요하고, 독자가 늘면 구독과 캐시가 필요하다. 배포한 뒤에는 느린 요청과 실패를 설명해야 한다. 이 권은 그 요구가 생기는 순서로 코드를 발전시킨다.

## 무엇을 배우는가

특정 패키지의 옵션을 외우는 것보다 책임의 위치를 판단하는 능력을 기른다. 컨트롤러는 요청 경계를, 서비스는 작업을, 도메인 모델은 규칙을 맡는다. 하지만 첫 장부터 모든 계층과 인터페이스를 만들지는 않는다. 작은 구현이 어떤 실패를 드러내는지 확인한 뒤 필요한 만큼 구조를 바꾼다.

테스트는 완성 뒤에 붙이는 부록이 아니다. 4장에서 단위·모듈·요청 테스트의 역할을 배우고 이후 입력 검증, 발행 트랜잭션, 권한, 큐와 종료 동작을 같은 습관으로 확인한다. 성공한 응답뿐 아니라 실패한 요청이 데이터를 바꾸지 않는지도 살펴본다.

## 출발점과 실행 환경

TypeScript의 함수, 클래스, Promise와 기본 HTTP 개념을 알고 있다고 가정한다. Fluo 경험은 필요하지 않다. 본문은 Node.js 24, pnpm 10, Fastify, PostgreSQL과 Prisma를 기준으로 한다. Redis, 큐, 이메일은 해당 기능이 필요해지는 장에서 도입한다. 모든 인프라를 첫날부터 설치할 필요는 없다.

독자가 만드는 앱은 CLI로 생성한 fluo-blog다. 애플리케이션의 파일 경로와 Fluo 저장소의 구현 근거 경로를 구분한다. 예제 블록이 완전한 파일인지, 기존 코드에 적용할 부분 구현인지 본문에서 밝힌다. 패키지의 실제 동작은 현재 README와 행동 계약을 기준으로 한다.

[짧은 HTTP 실습](../../apps/docs/content/docs/tutorial/index.ko.mdx)과 [실행 가능한 초기 체크포인트](../../examples/fluo-blog/README.ko.md)는 첫 HTTP·DI·검증 흐름을 비교할 때 쓸 수 있다. 이 자료가 이 권의 데이터베이스, 인증, 구독 기능까지 구현한 완성 앱을 제공하는 것은 아니다.

## 권의 진행

앞의 네 장에서 한 기능을 실행하고 테스트한다. 이어서 상태, DTO, 응답 모델, 오류 계약을 분리하고 데이터를 저장한다. 사용자와 권한이 생긴 뒤 공개 화면, 파일과 구독을 추가한다. 마지막에는 예약 작업, 관측, readiness와 종료를 연결해 첫 출시를 검토한다.

각 장의 실패 사례와 선택 기준을 함께 읽는다. 개발 환경의 메모리 구현, 테스트 대역, 실제 외부 시스템은 서로 다른 증거다. 외부 서비스가 필요한 실험은 환경과 재현 절차를 확인하고 직접 수행한다. 원고에 실린 명령 자체를 운영 안전성의 증명으로 취급하지 않는다.

## 다음 권으로 가져갈 것

이 권의 끝에는 accounts와 content 모듈, 사용자 식별자와 인증 정책, 설정, 배포, 관측의 기반이 남는다. 다음 권에서는 이것을 버리고 새 상점을 만들지 않는다. 블로그를 좋아하는 독자들이 티셔츠와 스티커를 요청하면서 같은 서비스에 상거래 기능을 붙인다.
