## The Publish Button Starts Waiting for the Mail Server

FluoBlog readers ask for subscriptions because they want to read the next post too. The operator initially plans to query the recipient list after publishing and send emails one by one. With ten readers, that is simple. But a single delayed delivery slows the entire publishing request, and if the browser resubmits after a timeout, people who already received the email receive it again. Even rolling back the publishing transaction because email failed cannot recall mail that has already gone out.

This chapter separates three facts: whether the post was published in PostgreSQL, whether the work to deliver it was recorded, and whether the mail provider accepted a particular recipient. `@fluojs/queue` passes the second piece of work to a worker for execution, while `@fluojs/email` hands messages to an explicitly registered transport. We do not interpret a Redis connection or a successful `enqueue()` as arrival in a reader's inbox.

The post is still the `Post` from the previous chapters. Its ID is a positive integer, and an account's subject is a string. The `draft -> published` transition occurs only once in the existing publishing transaction. Published posts are immutable, so there is no feature that resends notifications whenever a title is edited. The schemas and job classes below are additional code owned by this product, not tables generated by registering packages.

The exercise's email transport only records messages in memory. It does not send real SMTP mail or call an external service. Integration reproduction using PostgreSQL and Redis takes place in your isolated development environment; we do not claim to have executed it while writing the manuscript.

## Recording Consent and Address Verification as Subscription State

A logged-in user entering an email address does not prove they own it. We therefore separate requesting a subscription from confirming it. Below are the **field additions and new models** for `prisma/schema.prisma`. Retain `Post.publication PostPublication?` from Chapter 11 and the `id Int`, `postId @unique`, `actorId`, `version`, `publishedAt`, and `post` relation in `PostPublication`. Do not create a separate `Publication` model. Add `subscription Subscription?` to the existing `User` and `deliveries PostDelivery[]` to the existing `PostPublication`.

This migration connects subscriber users and existing publication records through foreign keys. It neither removes `actorId` from past `PostPublication` records nor renumbers their IDs, and it does not retroactively create delivery rows for past publications. Starting with publications after this chapter, we expand the active subscribers at the time into delivery rows.

`PostDelivery.address` is a snapshot of the address at publication time. A later change to an account's address must not silently redirect old work to the new address. Immediately before executing the job, we compare it with the current subscription address and cancel if it differs. Subscriptions with `active` turned off are excluded in the same way. The decision boundary for unsubscription is the worker's last read of subscription state. If an unsubscription commits immediately after that read, delivery already in progress may still go out. We do not guarantee cancellation of mail already handed to the transport.

The following `src/subscriptions/subscriptions.ts` is a complete service file for requests and confirmations. It injects the `PrismaService` exposed globally by Chapter 10's root-owned `BlogDatabaseModule`. Pass the verified principal's subject as `userId`, not a value from the HTTP body. We register the actual HTTP wiring for requesting, confirming, and unsubscribing later.

```ts
import { createHash, randomBytes } from 'node:crypto';
import { Inject } from '@fluojs/core';
import { BadRequestException } from '@fluojs/http';
import { EmailService } from '@fluojs/email';
import { PrismaService } from '@fluojs/prisma';
import type { PrismaClient } from '@prisma/client';

const digest = (token: string) => createHash('sha256').update(token).digest('hex');

@Inject(PrismaService, EmailService)
export class Subscriptions {
  constructor(
    private readonly prisma: PrismaService<PrismaClient>,
    private readonly email: EmailService,
  ) {}

  async request(userId: string, address: string) {
    const normalized = address.trim();
    if (normalized.length > 254 ||
        !/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(normalized)) {
      throw new BadRequestException('Invalid email address');
    }
    const token = randomBytes(32).toString('hex');
    await this.prisma.current().subscription.upsert({
      where: { userId },
      create: {
        userId, address: normalized, tokenHash: digest(token),
        expiresAt: new Date(Date.now() + 30 * 60 * 1000),
      },
      update: {
        address: normalized, active: false, tokenHash: digest(token),
        expiresAt: new Date(Date.now() + 30 * 60 * 1000),
      },
    });
    const receipt = await this.email.send({
      to: normalized,
      subject: 'Confirm your FluoBlog subscription',
      text: `Paste this code into the subscription confirmation form: ${token}`,
    });
    return receipt.accepted.length === 1 &&
      receipt.pending.length === 0 && receipt.rejected.length === 0;
  }

  async confirm(userId: string, token: string) {
    if (!/^[0-9a-f]{64}$/.test(token)) {
      throw new BadRequestException('Invalid confirmation code');
    }
    const result = await this.prisma.current().subscription.updateMany({
      where: {
        userId, active: false, tokenHash: digest(token),
        expiresAt: { gt: new Date() },
      },
      data: { active: true, tokenHash: null, expiresAt: null },
    });
    if (result.count !== 1) {
      throw new BadRequestException('Confirmation expired or already used');
    }
  }

  async unsubscribe(userId: string) {
    await this.prisma.current().subscription.updateMany({
      where: { userId },
      data: { active: false, tokenHash: null, expiresAt: null },
    });
  }
}
```

The confirmation code is pasted from the email into the confirmation form, not placed in a URL. This avoids leaving secrets in access-log URLs and works with the native forms from Chapter 17. Do not include the raw code in HTTP responses or application logs. If email sending fails, the pending subscription remains but does not become active. Requesting again replaces the code, so the previous one can no longer be used.

This simple implementation sends the confirmation email once within the signup request. Provider latency therefore affects only subscription requests, not publishing. Apply the limits from Chapter 16 to the request API to control repeated sending. If signups grow substantially, confirmation emails can also move to a separate delivery ledger, but we begin by moving the core post-notification path to a queue. The first priority is not to confuse address verification with a format check.

## Saving Delivery Intent Alongside Publication

If we only call `enqueue()` after committing the post, a process crash in between loses the notification. Enqueuing first, on the other hand, can announce a post that has not committed. In this chapter, we save `PostPublication` and `PostDelivery` inside the existing publishing transaction, then dispatch pending rows to the queue after commit. This is a delivery ledger built by the application itself. It does not create a distributed transaction between PostgreSQL and Redis.

The following `src/subscriptions/record-publication-deliveries.ts` is a complete function file. It does not create the publication ledger; it attaches delivery intent to **the ID of a publication record already created in the same transaction**. It does not open a separate database or another transaction.

```ts
import { randomUUID } from 'node:crypto';
import type { Prisma } from '@prisma/client';

export async function recordPublicationDeliveries(
  tx: Prisma.TransactionClient, publicationId: number,
): Promise<void> {
  const subscribers = await tx.subscription.findMany({
    where: { active: true },
    select: { userId: true, address: true },
    orderBy: { userId: 'asc' },
  });
  for (let offset = 0; offset < subscribers.length; offset += 200) {
    await tx.postDelivery.createMany({
      data: subscribers.slice(offset, offset + 200).map((subscriber) => ({
        id: randomUUID(),
        publicationId,
        subscriberId: subscriber.userId,
        address: subscriber.address,
      })),
    });
  }
}
```

The uniqueness of `PostPublication.postId` and the existing conditional publishing update prevent duplicate publication. Delivery rows are also unique on `(publicationId, subscriberId)`. If inserting a delivery fails, making the post public and the audit record, including `actorId`, roll back too. Manual `POST /posts/:id/publish` requests execute this code through the existing `PostWritingService -> PostsService -> PublishingService.publish` connection. Repeated dispatches use the already finalized rows instead of repeatedly expanding a new subscriber list. If a user's subscription commit overlaps the subscriber-list query during publication, that user becomes a recipient of this publication or only of subsequent publications according to PostgreSQL visibility for that SQL query.

This implementation fits the current small subscriber list. The entire queried list remains in memory, and inserting in batches of 200 does not shorten the overall transaction time. With hundreds of thousands of subscribers, publishing should record only the publication, with a separate fan-out job that has a cursor and a recipient cutoff time. Instead of reproducing that system from the start, observe the limits of the current choice in numbers. Recording publishing transaction latency alongside recipient count helps determine when to switch.

## Enqueuing the Exact Job Class and Handling One Address at a Time

The queue payload contains only one delivery ID. Do not serialize Prisma objects, `Date` values, functions, or email transports. Jobs are stored as JSON objects and restored with the registered prototype, but you must not expect the constructor to run again. The constructor identity of `new SendPostEmailJob(id)` is the basis for finding its worker, so a plain object with the same shape or a copied class is not a valid producer.

The following `src/subscriptions/email-jobs.ts` is a complete job file. It reuses the global `PrismaService` and `AppSettings`. Keep `jobName` fixed independently of refactored class names to preserve the identity of jobs already stored in Redis.

```ts
import { Inject } from '@fluojs/core';
import { EmailService } from '@fluojs/email';
import { QueueLifecycleService, QueueWorker } from '@fluojs/queue';
import { PrismaService } from '@fluojs/prisma';
import type { PrismaClient } from '@prisma/client';
import { AppSettings } from '../config/app-settings.js';

export class SendPostEmailJob {
  constructor(public readonly deliveryId: string) {}
}

export class AmbiguousDeliveryError extends Error {
  constructor(readonly deliveryId: string) {
    super(`Delivery requires reconciliation: ${deliveryId}`);
  }
}

@Inject(PrismaService, QueueLifecycleService)
export class PendingEmailDispatcher {
  constructor(
    private readonly prisma: PrismaService<PrismaClient>,
    private readonly queue: QueueLifecycleService,
  ) {}

  async dispatchPending(): Promise<number> {
    let cursor: string | undefined;
    let dispatched = 0;
    for (;;) {
      const rows = await this.prisma.current().postDelivery.findMany({
        where: { status: 'pending' },
        select: { id: true, dispatchVersion: true },
        orderBy: { id: 'asc' }, take: 100,
        ...(cursor ? { cursor: { id: cursor }, skip: 1 } : {}),
      });
      if (rows.length === 0) return dispatched;
      await this.queue.enqueueMany(rows.map((row) => ({
        job: new SendPostEmailJob(row.id),
        options: { deduplicationKey: `post-email:${row.id}:${row.dispatchVersion}` },
      })));
      dispatched += rows.length;
      cursor = rows[rows.length - 1]?.id;
    }
  }
}

@Inject(PrismaService, EmailService, AppSettings)
@QueueWorker(SendPostEmailJob, {
  jobName: 'blog-post-email-v1',
  concurrency: 4,
  attempts: 3,
  backoff: { type: 'exponential', delayMs: 1000 },
})
export class PostEmailWorker {
  constructor(
    private readonly prisma: PrismaService<PrismaClient>,
    private readonly email: EmailService,
    private readonly settings: AppSettings,
  ) {}

  async handle(job: SendPostEmailJob): Promise<void> {
    const current = await this.prisma.current().postDelivery.findUnique({
      where: { id: job.deliveryId },
    });
    if (!current) return;
    if (current.status === 'sending' || current.status === 'uncertain') {
      throw new AmbiguousDeliveryError(current.id);
    }
    if (current.status !== 'pending') return;
    const claim = await this.prisma.current().postDelivery.updateMany({
      where: { id: current.id, status: 'pending' },
      data: { status: 'sending' },
    });
    if (claim.count !== 1) return;

    try {
      const delivery = await this.prisma.current().postDelivery.findUniqueOrThrow({
        where: { id: current.id },
        include: { subscription: true, publication: { include: { post: true } } },
      });
      if (!delivery.subscription.active ||
          delivery.subscription.address !== delivery.address) {
        await this.prisma.current().postDelivery.update({
          where: { id: delivery.id }, data: { status: 'cancelled' },
        });
        return;
      }
      const receipt = await this.email.send({
        to: delivery.address,
        subject: `New post: ${delivery.publication.post.title}`,
        text: `${delivery.publication.post.title}\n` +
          `${this.settings.publicOrigin}/posts/${delivery.publication.postId}/read\n` +
          'Manage your subscription from your FluoBlog account.',
        metadata: { deliveryId: delivery.id },
      });
      const accepted = receipt.accepted.length === 1 &&
        receipt.pending.length === 0 && receipt.rejected.length === 0;
      const rejected = receipt.accepted.length === 0 &&
        receipt.pending.length === 0 && receipt.rejected.length === 1;
      await this.prisma.current().postDelivery.update({
        where: { id: delivery.id },
        data: {
          status: accepted ? 'accepted' : rejected ? 'rejected' : 'uncertain',
          messageId: receipt.messageId,
        },
      });
      if (!accepted && !rejected) throw new AmbiguousDeliveryError(delivery.id);
    } catch (error) {
      await this.prisma.current().postDelivery.updateMany({
        where: { id: current.id, status: 'sending' },
        data: { status: 'uncertain' },
      });
      throw error;
    }
  }
}
```

Putting one address in each delivery avoids resending to several successful recipients because one recipient failed. `EmailService.send()` preserves `accepted`, `pending`, and `rejected`. Treating a resolved Promise alone as success misses partial failures. This worker's `accepted` means the provider accepted the message; it does not confirm spam classification or final arrival in an inbox.

A PostgreSQL conditional update claims `pending -> sending`. Even if two distributed workers see the same delivery, only one begins sending. But if the process dies in `sending`, we do not know whether delivery actually occurred. On encountering that row again, the code does not automatically send it; it raises `AmbiguousDeliveryError`. Instead of pretending delivery is duplicate-free, we expose the boundary where duplicates are possible to the operator.

Queue retries help rerun failures such as database errors before the claim. Errors after sending begins leave `uncertain` in the ledger and produce the same warning on retry, so configuring three attempts does not mean three emails. This conservative policy prioritizes preventing uncertain duplicate sends over availability. If a missing notification is worse than some probability of duplication, you can change the retry policy. Even then, do not call it exactly-once without a provider idempotency contract.

## Making Redis and Email Ownership Explicit

First, complete the HTTP wiring. The **complete `src/subscriptions/subscriptions-controller.ts`** provides three POST APIs using cookie authentication together with native forms. Users submit requests, confirmations, and unsubscriptions from `/subscriptions`, returning to the GET with 303 on success. JSON requests must pass the same field checks, but this route's success contract is 303, not a JSON response. Users must first log in through Chapter 17's login page; we do not accept `userId` through a hidden input.

## Reading the Ledger Before Sending Again

The registered `EmailDispatchSchedule.tick()` calls `PendingEmailDispatcher.dispatchPending()` every 30 seconds. Cron registers schedules during `onApplicationBootstrap`, while Queue workers start after the entire app reaches bootstrap-ready, so do not describe these as the same ready signal. If enqueueing before readiness or a Redis outage causes an error, it propagates to Cron's error boundary and the pending rows remain. The next tick rereads the same ledger. Rows created before the cursor position during a query are also picked up on the next run. Chapter 21 retains this caller and adds only a publishing tick.

`enqueueMany()` records a valid batch for one worker queue through a single BullMQ `addBulk()` call. It does not make multiple pages or a PostgreSQL transaction atomic together. Even if a lost response causes the same page to be sent again, the `deduplicationKey` derived from the delivery ID and dispatch version is unchanged, so it uses the same backing job identity. Do not generalize this into permanent duplicate prevention after completed or failed jobs have been removed. Terminal-state checks in the database ledger are the longer-lived defense.

Operational inspection looks at both the queue and the database. `queue.inspectDeadLetters('blog-post-email-v1', { limit: 25 })` is read-only and skips malformed records. Default dead-letter retention keeps the most recent 1,000 records per job; it is not a permanent audit log of every failure. Also inspect counts of `sending`, `uncertain`, and `rejected` rows and old `updatedAt` values. `rejected` means the provider rejected the message, whereas `uncertain` means the result could not be established; they require different responses.

The following is the complete administrative function in `src/subscriptions/reconcile-delivery.ts`. Call it only through an authorized administrative path after confirming that the worker has stopped or that the relevant job has reached terminal failure. Choose `accepted` when provider records confirm acceptance. Choose `retry` when non-acceptance has been confirmed or the duplicate risk has been explicitly accepted. Since a failed BullMQ job may remain under the same deduplication key, increment the dispatch version as well when deciding to resend.

```ts
import { ConflictException } from '@fluojs/http';
import type { PrismaService } from '@fluojs/prisma';
import type { PrismaClient } from '@prisma/client';

export async function reconcileDelivery(
  prisma: PrismaService<PrismaClient>, id: string, decision: 'accepted' | 'retry',
) {
  const result = await prisma.current().postDelivery.updateMany({
    where: { id, status: { in: ['sending', 'uncertain', 'rejected'] } },
    data: decision === 'accepted'
      ? { status: 'accepted' }
      : { status: 'pending', dispatchVersion: { increment: 1 }, messageId: null },
  });
  if (result.count !== 1) {
    throw new ConflictException('Delivery state changed');
  }
}
```

This function does not replace querying the provider. Exposing a button that resets rows to pending without evidence would defeat the conservatively designed worker. The administrator records the basis for the decision in a separate operational record and calls the dispatcher after retry. In the recording-transport exercise, you can compare `metadata.deliveryId` in the retained messages. For a real provider, examine the search and idempotency capabilities that provider supports.

## Failure Experiments Without Waiting on Timing

First, request a subscription through the recording transport, extract the confirmation code from the email body retained by the test, and pass it to `confirm()`. The database's `active` should be true, and using the same code twice should return 400 on the second attempt. Recording a publication after unsubscription should create no new delivery for that user. If unsubscription commits after publication but before the worker reads the subscription, an already created delivery should finish as `cancelled`, and the transport's recording count should not increase.

The queue integration experiment requires Redis and PostgreSQL. Call `dispatchPending()` twice and subscribe to the actual worker-completion signal to await it. Reading the message array's length after a fixed sleep can pass or fail by chance on a slow machine. Separate Promises for when the test transport's `send` begins and when it is allowed to finish let you stop precisely at boundaries such as a database-recording failure immediately after acceptance. A bounded timeout exists to terminate failure, not as a time value from which to assume the work is done.

Make a partial-failure transport resolve normally with `accepted: []`, `rejected: ['reader@example.test']`, and `pending: []`. The expected ledger state is `rejected`, not `accepted`. If you simulate a network error after the provider accepted the message, the ledger should become `uncertain`, and retrying the same job must not increase the transport call count. When a database read fails before the claim and then recovers, the next attempt should be able to send.

For the shutdown experiment, hold an in-progress transport send at an event boundary and begin closing the app. New enqueue operations should be rejected, and the ledger and queue state should explain how already started work finished. Do not treat the shutdown timeout as an exactly-once guarantee. A response lost during shutdown and a failure to record a dead letter are independent failures too.
