# Serving the First Post over HTTP

## Turning a Successful Run into Success for the Reader

In the previous chapter, we checked the path for starting and stopping the server. `/greeting` is a good sign that the development environment works, but visitors to a blog want to read posts, not greetings. The operator decides to send a colleague the URL of the first post. With only one post to begin with, we need neither an editing screen nor a database. Readers only need to find the post in a list, copy its URL, and learn that a post does not exist when they use a wrong address.

Defining the requirement merely as returning JSON would miss something important. A server that returns the first post even for `/posts/999` succeeds at returning JSON but shows the reader false information. Conversely, treating an empty list as a server error makes the normal state of having no posts yet look like an outage. An HTTP contract includes not just the content, but which status to return under which conditions.

In this chapter, we create only two routes: `GET /posts` and `GET /posts/:id`. A successful list response is an array; a successful detail response is an object. We use `400` for an ID with invalid syntax and `404` for a well-formed ID that does not exist. There is no `POST` feature for creating posts yet. We will not accept every HTTP method through a single handler to imitate a write operation that does not exist.

The first seed has three fixed fields: `id` is the number `1`, `title` is `Hello, Fluo!`, and `content` is `My first post.`. At this stage, the model has no author, publication status, or version. Instead of filling unnecessary fields with temporary values, we will introduce them later alongside the requirements that make them necessary. Keeping this small model stable, rather than renaming it in each chapter, lets tests and data storage connect naturally later.

## First, Confirm That the Route Does Not Exist Yet

With the development server running in the state from the previous chapter, send this request.

```bash
curl -i http://127.0.0.1:3000/posts
```

If the route has not yet been registered, the expected result is `404`. That is the starting point for this feature. If you already see posts, check whether you are looking at a different, older app and which process owns the port. Adding code without first observing the failure makes it difficult to tell whether your change is what caused the success.

Now create the `src/posts/` directory. The following is the **complete file** for `src/posts/post.ts`.

```ts
export interface Post {
  id: number;
  title: string;
  content: string;
}
```

This interface is a data shape owned by the application. It is not a database model automatically generated by Fluo. TypeScript can catch mistakes involving numeric IDs while you write code, but it does not convert a string received over the network into a number or inspect a deployed response at runtime.

Start with the smallest implementation. The following is the **first complete file** for `src/posts/posts.controller.ts`. Later, we will replace the same file with an implementation that also supports detail queries.

```ts
import { Controller, Get } from '@fluojs/http';
import type { Post } from './post';

@Controller('/posts')
export class PostsController {
  @Get()
  list(): Post[] {
    return [
      { id: 1, title: 'Hello, Fluo!', content: 'My first post.' },
    ];
  }
}
```

`@Controller('/posts')` sets the route prefix for this class. The omitted argument to `@Get()` means an empty relative path, so the final route is `/posts`. It does not ignore the prefix and produce `/`. Nor is the file discovered automatically because its name is `posts.controller.ts`. It must be registered in a module.

The following is a **complete file** for `src/app.ts` that adds the controller while preserving the generated starter configuration. `ConfigModule`, `HealthModule`, and `GreetingModule` are existing registrations created by the CLI; this chapter's new feature is the single `controllers` entry.

```ts
import { Module } from '@fluojs/core';
import { ConfigModule } from '@fluojs/config';
import { HealthModule } from '@fluojs/runtime';
import { GreetingModule } from './greeting/greeting.module';
import { PostsController } from './posts/posts.controller';

@Module({
  global: true,
  imports: [
    ConfigModule.forRoot({
      envFile: '.env',
      processEnv: process.env,
    }),
    GreetingModule,
    HealthModule.forRoot(),
  ],
  controllers: [PostsController],
})
export class AppModule {}
```

`src/main.ts` continues to run this `AppModule`. The new controller has no dependencies yet, so we do not add an empty constructor or a meaningless `@Inject()`. When a dependency arises, we will inject it with an actual token in the next chapter. Avoid both using DI as decoration when registration is sufficient and hiding a dependency through manual construction once one exists.

After the development process finishes restarting, request `/posts` again. The expected status is `200`, with the following body.

```json
[
  {
    "id": 1,
    "title": "Hello, Fluo!",
    "content": "My first post."
  }
]
```

This JSON is a formatted view of the expected response for readability. The actual response need not have identical whitespace or property display order. Clients should depend on the distinction between arrays and objects, the field names, and the types of the values. The framework writes a returned plain object as the response, so do not call `JSON.stringify()` yourself and return a string. Converting it to a string makes it easy to confuse a structured value with an already encoded representation.

## Converting the Path String into a Post ID

The colleague wants a URL for a particular post rather than the list. We choose `/posts/1`. Here, `1` is a string in the HTTP path, while the application's `Post.id` is a number. Just as constructor type inference did not replace DI tokens, a parameter type annotation does not replace HTTP input conversion.

Create the **complete file** `src/posts/post-params.dto.ts`.

```ts
import { FromPath } from '@fluojs/http';

export class PostParamsDto {
  @FromPath('id')
  id = '';
}
```

A DTO is a class that declares what to extract from a request. `@FromPath('id')` selects the path variable's name. The detail handler must also have `@RequestDto(PostParamsDto)` for the binding declarations in this class to be used. Leaving only the type annotation `get(input: PostParamsDto)` is not runtime binding configuration.

There is also a reason for initializing the field as `id = ''`. Under this book's Babel standard-decorator configuration, declaring a decorated field as `id!: string` is not a supported authoring form. The initial value makes the field to be assigned by the binder explicit while respecting the transformation boundary. It does not mean that an empty string is accepted as a valid ID.

Keep the input policy in a separate small function. The following is the **complete file** for `src/posts/post-id.ts`.

```ts
import { BadRequestException } from '@fluojs/http';

export function parsePostId(value: string): number {
  if (!/^[1-9][0-9]*$/.test(value)) {
    throw new BadRequestException('Post id must be a positive decimal integer.');
  }

  const id = Number(value);
  if (!Number.isSafeInteger(id)) {
    throw new BadRequestException('Post id is outside the supported integer range.');
  }

  return id;
}
```

`Number.parseInt('1garbage', 10)` can read the leading `1`. Our API does not accept that as a request for the first post. `1.5`, `0`, negative numbers, and `01` with a leading zero are also outside the ID notation defined in this chapter. In particular, values beyond JavaScript's safe integer range, such as `9007199254740992`, are not used as exact identifiers even if they can be converted to numbers.

Strict notation has a cost. If you previously distributed `/posts/01` externally, a change that rejects it breaks existing links. This app is choosing its first URLs, so we can select a single notation. For a service with existing users, you must first observe the inputs in use and decide on a redirect or migration policy. Do not transplant this regular expression into an existing API simply because it is short.

This function is not a general-purpose replacement for all DTO validation. For now, it is a small HTTP boundary that helps us understand the policy for one path variable. When title length, optional fields, and multiple input sources become relevant, we will organize validation and conversion in Chapter 6. We will not build a complex validation framework here or unconditionally correct invalid values to `1`.

## The Final Controller: Distinguishing a Detail Result from a Missing Post

Now replace `src/posts/posts.controller.ts` with the following **complete file**. It uses the `Post`, `PostParamsDto`, and `parsePostId` created above, and the registration in `src/app.ts` stays the same.

```ts
import { Controller, Get, NotFoundException, RequestDto } from '@fluojs/http';
import type { Post } from './post';
import { parsePostId } from './post-id';
import { PostParamsDto } from './post-params.dto';

@Controller('/posts')
export class PostsController {
  private readonly posts: Post[] = [
    { id: 1, title: 'Hello, Fluo!', content: 'My first post.' },
  ];

  @Get()
  list(): Post[] {
    return this.posts.map((post) => ({ ...post }));
  }

  @Get('/:id')
  @RequestDto(PostParamsDto)
  get(input: PostParamsDto): Post {
    const id = parsePostId(input.id);
    const post = this.posts.find((candidate) => candidate.id === id);

    if (!post) {
      throw new NotFoundException('Post not found.');
    }

    return { ...post };
  }
}
```

We moved the array into a field so that list and detail queries see the same dataset. Putting a separate seed in each handler would allow a title change on one side to make the list and detail look like different posts. Having the controller store the data is only a temporary starting point, however. In the next chapter, we will see which changes this arrangement makes difficult and separate the logic.

Each return value is copied so that callers do not also receive permission to modify internal objects. An HTTP client that parses a response cannot directly change server memory. The concern is direct calls and tests within the same process. The current fields are only numbers and strings, so a shallow copy is sufficient. If nested arrays or objects appear later, we must reconsider the fact that the same copy does not isolate their contents.

`NotFoundException` is not merely an error with `404` in its name. The current HTTP package's exception carries status `404` and code `NOT_FOUND`, and the dispatcher writes it in the standard error representation. For example, the body for a missing post has this form.

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Post not found.",
    "status": 404
  }
}
```

Middleware that adds a request ID or similar information may introduce additional fields. Tests should therefore check the required error code and status rather than asserting that no arbitrary diagnostic field can ever be present. We have no author identifier or authentication information yet, so we do not invent those values in this response.

Expressing a missing post as `return null` may combine it with a successful `200` response and leave the client to infer the meaning separately. Likewise, `return { error: 'not found' }` is a plain object that does not declare an HTTP error. On the other hand, catching every exception and converting it to `404` disguises programming defects and storage failures as a missing post. The key to this boundary is to represent known failures with the intended exceptions and not turn unknown failures into absent data.

## An Input Table Proves More Than One Successful Response

With the development server running, check the routes one by one.

```bash
curl -i http://127.0.0.1:3000/posts
curl -i http://127.0.0.1:3000/posts/1
curl -i http://127.0.0.1:3000/posts/999
curl -i http://127.0.0.1:3000/posts/1garbage
curl -i http://127.0.0.1:3000/posts/9007199254740992
```

The expected statuses, in order, are `200`, `200`, `404`, `400`, and `400`. The first item in the list and the detail object should represent the same seed. Because `999` has valid input syntax, it proceeds to a query and is then classified as missing data. The last two requests violate the input policy and are rejected before looking for a post. This distinction also lets you interpret invalid links and missing posts as different causes in operational logs.

Instead of comparing the results by hand, you can keep a small check against the real listener. The following is a **complete Node.js experiment file** that can live at `scripts/check-posts.mjs` in the generated project. It requires no additional test library.

```js
import assert from 'node:assert/strict';

const origin = process.env.BLOG_ORIGIN ?? 'http://127.0.0.1:3000';
const expected = { id: 1, title: 'Hello, Fluo!', content: 'My first post.' };

async function request(path) {
  return fetch(new URL(path, origin), {
    headers: { accept: 'application/json' },
    signal: AbortSignal.timeout(5000),
  });
}

const list = await request('/posts');
assert.equal(list.status, 200);
assert.deepEqual(await list.json(), [expected]);

const detail = await request('/posts/1');
assert.equal(detail.status, 200);
assert.deepEqual(await detail.json(), expected);

for (const [path, status, code] of [
  ['/posts/999', 404, 'NOT_FOUND'],
  ['/posts/1garbage', 400, 'BAD_REQUEST'],
  ['/posts/9007199254740992', 400, 'BAD_REQUEST'],
]) {
  const response = await request(path);
  assert.equal(response.status, status);
  const payload = await response.json();
  assert.equal(payload.error.status, status);
  assert.equal(payload.error.code, code);
}

console.log('Post HTTP checks passed.');
```

```bash
node scripts/check-posts.mjs
```

This file does not start the server. It sends requests to a local server whose startup you have already confirmed, so it does not insert an arbitrary wait. `AbortSignal.timeout(5000)` is an upper bound that ends a check if the server does not respond, not a mechanism for waiting a little while until success. When every assertion passes, the final message is printed; if any assertion differs, the script exits with an error. The manuscript presents the expected result of this procedure, not a passing log for the newly written experiment.

We can now produce meaningful failures as well. Temporarily removing `@RequestDto(PostParamsDto)` should reveal, through a detail request, that a type annotation alone does not preserve binding. Removing `PostsController` from `controllers` should cause even the list to return `404`. Replacing `parsePostId` with a conversion that reads only the leading portion should make the `1garbage` check fail. Restore the correct code after checking each case. These three failures affect different boundaries; grouping all of them under routes not working would obscure the causes.

## Keeping the Query Feature Small

List and detail queries do not change data. Sending the same GET twice should read the same seed, without IDs increasing or posts disappearing based on query order. Concurrent requests at this stage observe the same read-only state. If you start two servers, each process has its own seed in memory; this is not a shared-data design. Identical results now are not evidence of persistence or consistency between processes.

The current list has neither a page-size limit nor a publication-status filter. It is enough for exposing one post, but not for thousands of posts and drafts. That does not mean putting every future field into the first controller. Adding boundaries when there is a reason to change, while protecting existing observable results, makes it easier to judge which complexity is needed.

We also use only a small part of the route syntax. You can declare a full segment as a path variable, as in `/posts/:id`, but that does not mean `:id.json`, `post-:id`, or paths that look like regular expressions are all supported. Fluo's controller paths use literal segments and full-segment parameters as their basic contract. Bringing in familiar syntax from another router can cause rejection at startup or create a boundary different from the one you expect, so check the current public contract.

By the end of this chapter, readers can read the first post through a list and an individual URL. There is no repository yet, the seed lives in the controller, and ID parsing is a separate small function. The next requirement is to use the same query logic from code outside HTTP. At that point, rather than constructing a controller directly, we will create a service that owns the data and a module that connects the service. The next chapter's refactoring changes only this internal structure, not the URLs or JSON.
