# 3권 — Inside Fluo: 우리가 만든 서비스의 엔진룸

[시리즈 소개](../README.ko.md) · [전체 목차](./toc.ko.md)

게시글과 주문을 처리하는 코드는 이미 손에 있다. 이제 PostsService가 언제 생성되는지, 같은 요청 안에서 어떤 인스턴스가 공유되는지, 초기화가 실패하면 무엇을 정리하는지 궁금해진다. 이 권은 앞의 두 권에서 만든 서비스의 실행을 Fluo의 실제 소스와 테스트로 설명한다.

## 구현 목록이 아니라 질문에서 시작한다

공개 API에서 내부 함수로 이동할 때마다 왜 그 경계가 필요한지 묻는다. 코드를 읽는 순서는 파일의 알파벳 순서가 아니다. 주문 요청 한 건을 출발점으로 데코레이터 메타데이터, Provider 정규화, 의존성 해석, 모듈 그래프, bootstrap과 요청 파이프라인을 연결한다.

줄 번호는 시간이 지나면 바뀐다. 따라서 설명은 안정적인 파일·심볼·행동 계약에 연결하고, 작은 실행 실험과 회귀 테스트로 확인한다. 소스를 읽었다는 사실과 어떤 런타임에서 동작을 검증했다는 사실을 구분한다.

## 읽기 전에 필요한 것

TypeScript, Promise, HTTP 요청의 기본 흐름과 Fluo의 모듈·DI 사용법을 알고 있다고 가정한다. 모든 브로커를 실행하거나 2권의 비교 실습을 전부 완료할 필요는 없다. 게시글 또는 주문 모듈 하나를 재현 가능한 입력으로 삼으면 된다.

저장소 소스 분석은 같은 checkout의 공개 export, 구현과 테스트를 함께 읽는다. 문서의 사용 예제를 수정하기 전에 패키지 README와 docs/contracts의 보장 범위를 확인한다. internal 경로에 존재한다는 이유만으로 외부 애플리케이션에서 가져다 쓸 수 있다고 가정하지 않는다.

## 런타임 차이를 숨기지 않는다

Node.js의 Fastify·raw Node·Express는 같은 서버 소유권을 가진 단일 구현이 아니다. Bun, Deno와 Cloudflare Workers는 Fetch 요청을 사용해도 시작·종료·환경 자원의 경계가 다르다. Next.js 안에서는 호스트가 서버와 번들을 소유하므로 별도의 listener를 열어야 한다고 가정하지 않는다.

공통 계약을 찾되, 모든 플랫폼이 모든 기능을 제공한다고 일반화하지 않는다. 어댑터를 만들 때는 의도한 지원 범위를 선언하고 conformance와 portability 테스트로 그 범위를 검증한다. 불가능한 기능을 조용한 fallback으로 숨기는 대신 경계를 명시한다.

## 이 권의 결과물

처음에는 소스를 읽고 동작을 설명한다. 이어서 커스텀 데코레이터, Provider 구성, 어댑터와 확장 패키지의 경계를 직접 설계한다. 마지막에는 실제 프레임워크 변경 하나를 실패 테스트, 구현, 문서, 마이그레이션과 함께 제출하는 과정을 다룬다.

성능은 주장 대신 측정으로 다룬다. 작은 벤치마크의 수치와 애플리케이션 요청 처리량을 구분하고, 캐시가 어떤 수명과 무효화 조건을 갖는지 확인한다. Studio와 inspection 출력은 이 판단을 돕는 진단 근거이며 실제 런타임 상태 전체를 자동으로 증명하지는 않는다.
