# Cache Products, but Do Not Trust the Cache Alone for Inventory Decisions

## Fast Product Pages and Correct Purchases Are Different Promises

On the day a new post appears on FluoBlog, thousands of readers click the logo T-shirt link beneath it at once. The post loads smoothly thanks to the cache introduced in Volume 1, but `/products` queries repeatedly read image URLs, product descriptions, and sale prices. The operations dashboard from the previous chapter assembles the same products, adding to database load. Caching public queries in the existing `CatalogModule` can reduce read costs. Wrapping `InventoryModule` in the same way, however, causes an entirely different kind of incident.

Suppose only one T-shirt remains. Two customers read `available: 1` from the same cache, and both successfully place an order. Responses are faster, but the shop has sold more units than it can sell. Reducing the TTL to one second does not prevent a race within that second. Sharing Redis only makes two servers read the same value; it does not combine their PostgreSQL transactions into one. We must distinguish between "the query results are the same" and "the right to reserve was acquired only once."

In this chapter, the cache owns **product cards for display**. The existing order transaction reassesses whether a purchase is allowed, the price at order time, discount application, and inventory reservation. If the price the customer saw has changed, the server must apply the existing purchase policy for confirming the new amount, not silently charge the cached price. It also determines `customerId` from the existing authenticated principal, not from a card or cart. We are changing just one read path while retaining the same blog accounts and order model.

## First, Narrow Down What to Store

Putting the entire DB model in the cache is convenient at first. But it mixes administrator-only supply costs, private product notes, account-specific discounts, and reservation information in one object. When several HTTP and GraphQL responses share that object, one cache-key mistake can expose information. The following type is an application-owned public read contract, not a model generated by Fluo.

The following block is the **complete file** `src/catalog/product-cards.ts`. `ProductCardSource.load()` is a port connecting the existing PostgreSQL/Prisma product query. It looks up the SKU in the `ProductVariant` from Chapter 3 and checks `active` and the parent `Product`'s publication status. It returns `null` when no corresponding public product exists, or only the specified fields when one does. `unitMinor` is a public field that converts `ProductVariant.priceMinor` to a decimal string, not a second price ledger. Convert the original `bigint` to a string before this boundary. `revision` is a product version added to the public card and incremented when its description or displayed price changes. It is distinct from an order's `version`.

```ts
import { Inject } from '@fluojs/core';
import { CacheService } from '@fluojs/cache-manager';

export interface ProductCard {
  sku: string;
  title: string;
  imageUrl: string;
  currency: 'KRW';
  unitMinor: string;
  revision: number;
}

export interface ProductCardSource {
  load(sku: string): Promise<ProductCard | null>;
}

export const PRODUCT_CARD_SOURCE = Symbol('shop.product-card-source');
export const CACHE_FAILURES = Symbol('shop.cache-failures');

export interface CacheFailures {
  record(operation: 'read' | 'write' | 'invalidate'): void;
}

@Inject(CacheService, PRODUCT_CARD_SOURCE, CACHE_FAILURES)
export class ProductCards {
  constructor(
    private readonly cache: CacheService,
    private readonly source: ProductCardSource,
    private readonly failures: CacheFailures,
  ) {}

  private key(sku: string): string {
    return `card:v1:${encodeURIComponent(sku)}`;
  }

  async get(sku: string): Promise<ProductCard | null> {
    const key = this.key(sku);
    try {
      const cached = await this.cache.get<ProductCard>(key);
      if (cached !== undefined) return cached;
    } catch {
      this.failures.record('read');
    }

    const card = await this.source.load(sku);
    if (card === null) return null;

    try {
      await this.cache.set(key, card, 30);
    } catch {
      this.failures.record('write');
    }
    return card;
  }

  async invalidate(sku: string): Promise<void> {
    try {
      await this.cache.del(this.key(sku));
    } catch {
      this.failures.record('invalidate');
    }
  }
}
```

Here, reads and writes are separate rather than using `remember()`. Manual `CacheService` calls propagate store failures to the caller. Catching the entire `remember()` call and querying the DB again can misclassify an original DB error as a cache failure, or query the DB twice when the query succeeded and only the cache write failed. The code above proceeds to the source when only the cache fails, while propagating source query failures unchanged. The application contract for `CacheFailures.record()` is a local counter update that does not throw. Instrumentation must not become a new dependency whose failure breaks the query.

A cache miss is `undefined`, while a product absent from the source is `null`. This first implementation does not cache missing products. To use caching against attacks involving nonexistent SKUs, decide on a separate short-lived negative-cache policy and a limit on the number of inputs. This implementation also does not coalesce concurrent misses. Within one process, `remember()` coalesces in-flight loaders for the same key, but it is not a distributed lock that combines loaders across instances. Measure DB load first, and add coalescing if needed while retaining the distinction between failures.

## Separate Ownership of the Redis Connection and the Cache

Do not blindly duplicate the Redis registration used by the queue and cache in Volume 1. The following `src/catalog/catalog-cache.module.ts` is a **complete composition file** that accepts the port implementation and instrumentation object when building the module graph. Add this function's return value to the existing `CatalogModule`'s `imports`, and inject `ProductCards` into the public query provider. This does not mean recreating the existing `CatalogModule`, accounts, or product write providers.

```ts
import { Module } from '@fluojs/core';
import { CacheModule } from '@fluojs/cache-manager';
import { RedisModule } from '@fluojs/redis';
import {
  CACHE_FAILURES,
  PRODUCT_CARD_SOURCE,
  ProductCards,
  type CacheFailures,
  type ProductCardSource,
} from './product-cards.js';

export function createCatalogCacheModule(
  source: ProductCardSource,
  failures: CacheFailures,
  redisHost: string,
) {
  @Module({
    imports: [
      RedisModule.forRoot({
        name: 'catalog-cache',
        host: redisHost,
        port: 6379,
        enableOfflineQueue: false,
        maxRetriesPerRequest: 1,
        commandTimeout: 500,
        lifecycle: { connectTimeoutMs: 2_000, quitTimeoutMs: 2_000 },
      }),
      CacheModule.forRoot({
        store: 'redis',
        ttl: 30,
        keyPrefix: 'fluo-blog:catalog-cache:',
        redis: { clientName: 'catalog-cache' },
        ttlJitter: { ratio: 0.1, mode: 'shorten' },
      }),
    ],
    providers: [
      { provide: PRODUCT_CARD_SOURCE, useValue: source },
      { provide: CACHE_FAILURES, useValue: failures },
      ProductCards,
    ],
    exports: [ProductCards],
  })
  class CatalogCacheModule {}

  return CatalogCacheModule;
}
```

Call the registration function once per application. Bootstrap rejects duplicate registration of the named Redis identity `catalog-cache`. The cache module selects this connection through `clientName` and provides `CacheService`. A named connection does not also acquire an unnamed `RedisService` alias. If you need the raw client, the public token is `getRedisClientToken('catalog-cache')`; for the JSON facade, it is `getRedisServiceToken('catalog-cache')`. This chapter's product cache does not use the facade directly, so we do not add an unnecessary second connection or provider.

`RedisModule` owns connection startup and shutdown. The `CacheService` wrapping the Redis store does not close the raw client. If instead you choose to pass a client you created directly through `redis.client`, the application owns connection and shutdown. A Pub/Sub connection switched into subscription mode must not be reused as this cache's command connection either.

Command timeouts limit the spread of a cache outage into thousands of slow requests. Lifecycle timeouts apply to startup and shutdown, not to every GET. The manual query above bypasses cache failures during operation, but startup itself can fail if the registered Redis cannot connect during bootstrap. If an "optional cache" must also be optional at deployment startup, you need a separate deployment policy that chooses memory registration at the configuration boundary. This chapter does not introduce a policy that silently switches stores during operation and leaves instances with different state.

TTL is measured in seconds. Applying shortening jitter to `30` gives each write an effective TTL of 27-30 seconds. `0` means no expiration, not disabled caching. Omitting TTL in the Redis store also defaults to no expiration, so specify a value for commerce cards. Jitter spreads out simultaneous expiration of popular keys; it does not solve a surge on one SKU or a source DB outage.

## Why an Old Price Reappears After Deletion

When an administrator changes a product price, first commit the DB transaction, then call `invalidate(sku)`. Reversing that order lets another request read the old DB value and refill the key you just deleted. But deleting after commit does not eliminate every race either. Server A can pause after reading the old value, server B can commit the new price and delete the key, and A can then store the old value.

`CacheService` has a mechanism by which `del()` or `reset()` on the same instance invalidates an in-flight `remember()` loader. That in-memory state is not shared with other servers. Moreover, the explicit `get()`/`set()` pair above does not participate in that loader tracking. Whether delayed product-card updates are acceptable is a product promise you must decide. If a source query finishes late, an old value can remain visible not for exactly 30 seconds after the DB change, but **for one TTL after the last time that value was populated**.

The following is a **complete source experiment file** you can place in `src/catalog/cache-race.experiment.ts`. Two `CacheService` instances share the same store to separate per-process state from store state. Because it uses a memory store, it does not verify the Redis network or TTL precision. It waits for a signal that the loader has started before deleting, so no arbitrary sleep is needed.

```ts
import assert from 'node:assert/strict';
import {
  CacheService,
  MemoryStore,
  type NormalizedCacheModuleOptions,
} from '@fluojs/cache-manager';

const options: NormalizedCacheModuleOptions = {
  global: false,
  httpKeyStrategy: 'route',
  keyPrefix: 'experiment:',
  principalScopeResolver: undefined,
  store: 'memory',
  ttl: 0,
};

export async function cacheRaceExperiment(): Promise<void> {
  const store = new MemoryStore();
  const reader = new CacheService(store, options);
  const editor = new CacheService(store, options);
  const entered = Promise.withResolvers<void>();
  const release = Promise.withResolvers<void>();
  const key = 'card:v1:TEE-BLACK-M';
  let deadline: ReturnType<typeof setTimeout> | undefined;
  const bound = new Promise<never>((_, reject) => {
    deadline = setTimeout(() => reject(new Error('Experiment timed out')), 1_000);
  });

  try {
    const pending = reader.remember(key, async () => {
      entered.resolve();
      await release.promise;
      return { unitMinor: '25000', revision: 1 };
    });
    await Promise.race([entered.promise, bound]);
    await editor.del(key);
    release.resolve();
    await pending;
    assert.deepEqual(await editor.get(key), {
      unitMinor: '25000',
      revision: 1,
    });
  } finally {
    clearTimeout(deadline);
    release.resolve();
    await Promise.all([reader.close(), editor.close()]);
  }
}
```

The expected result is that revision 1 is stored again even after deletion. This is not a test that breaks a package guarantee of distributed invalidation; it is an experiment confirming that no such guarantee exists. If you change `editor.del()` to `reader.del()`, the in-flight loader should return its value to the caller without refilling the key. Also change the expected value to `undefined` when verifying this, and compare the two boundaries. The experiment's `ttl: 0` is a test setting that keeps elapsed time out of the conclusion, not a recommended production value.

If even product descriptions must update immediately, you can combine immutable per-revision keys with an authoritative current-revision lookup. That introduces the cost of deciding where to read the current revision and how to change it atomically. Clearing the entire cache with `reset()` on every edit sends the read load back to the DB all at once. A dedicated `keyPrefix` is the ownership boundary for cache deletion; do not share it with queues, sessions, or idempotency records.

## Decide Inventory Through an Atomic Write

[`CacheService.update`](../../packages/cache-manager/README.md#atomic-updates) atomically mutates one cache value with a pure reducer, replacing an application's key queue. However, do not move the product-card query's database I/O into that reducer. A reducer that can rerun on conflict owns neither origin loading nor order side effects, and does not combine a PostgreSQL commit with a cache commit. Explicit Redis atomic opt-in does not make `remember` a distributed loader or automatically fence the late `set` above. [Volume 1's queue-free experiment](../01-fluoblog/ch20-caching.md#updating-one-cache-value-without-a-key-queue) is cache-only arithmetic; inventory reservation in this chapter remains the responsibility of the database transaction below.

Even when a product page says "in stock," that is guidance. The conditional update in the existing `InventoryModule` grants the final right to purchase. The following SQL is the **core statement of a PostgreSQL transaction using the existing Stock model**. `Stock.available` is the quantity available for reservation; we do not introduce a separate `reserved` total column or a second inventory table. `$1` is the validated positive integer quantity, and `$2` is the SKU confirmed by the server.

```sql
UPDATE "Stock"
SET "available" = "available" - $1
WHERE "sku" = $2
  AND "available" >= $1
RETURNING "sku", "available";
```

If no row is returned, the reservation fails. This statement, creation of the `Reservation` with composite key `(orderId, sku)`, and storage of the order snapshot belong to the **same DB transaction** built earlier. A duplicate purchase request returns the existing idempotency result. Running this SQL twice separately and checking for duplicates afterward may already have deducted inventory twice. On an exception or uniqueness conflict, roll back the entire transaction. Process multiple SKUs in a consistent sorted order, and leave no partial reservation if even one is short.

When payment is confirmed, the existing `OrderInventoryService.confirmPayment()` changes reservations to `consumed` without deducting inventory again. Cancellation before payment returns units only once for reservations that actually changed to `released`; refunds after payment leave a separate durable compensation record. The cache does not participate in this ledger's state transitions. Both the source query and inventory service use the same `PrismaService` provided by the root's `src/database/blog-database.module.ts`. Adding a cache is not a reason to create another DB registration.

Verify failure scenarios at their respective boundaries too. If a purchase is made while a product card retains an old price and `revision`, the new order's amount must snapshot the current price in the DB. Submit two purchases with different idempotency keys concurrently against a DB with one unit of stock: only one reservation should succeed, and the quantity must not become negative. Two requests with the same idempotency key must point to one order. Make the cache client's `get` and `set` reject separately: product queries must return the source result while the failure counter increases only for the corresponding operation. Conversely, make the source DB reject: the query failure must surface rather than masquerade as a cache outage.

Verify this DB race using transactions on two separate connections. A sequential test on a single connection or a `Map` substitute cannot verify PostgreSQL row locking and uniqueness races. During production shutdown, stop accepting requests, dispose of in-flight DB and cache work, and then close the connections. A cache miss returned during shutdown is no more evidence of a successful new reservation than it is during normal operation.

## The Limits of What a Cache Can Get Wrong

If public PostgreSQL queries are already fast enough for a small shop, choosing not to add a Redis cache is reasonable. The cost of maintaining network round trips, failure modes, and an invalidation policy can exceed the benefit of the hit rate. Separating public cards from authoritative purchase calculations first lets you make this decision without changing the store. When applying an HTTP cache interceptor directly, also remember that its default key ignores the query. Search and filters require query-aware keys, while language, currency, and price lists are even more explicit variation dimensions.

FluoShop now serves product guidance quickly while leaving decisions about money and inventory in the existing transactions. When international readers arrive in the next chapter, the same SKU will need cards in different languages. We will build on this boundary to keep Korean and English responses out of the same key and to address why translating a number does not change its currency.
