# 2권 — FluoShop: 인기를 얻은 블로그가 상점을 열다

[시리즈 소개](../README.ko.md) · [전체 목차](./toc.ko.md)

FluoBlog의 뉴스레터를 읽는 독자들이 로고 티셔츠와 스티커를 사고 싶다고 말한다. 이제 운영자는 같은 회원 계정과 웹사이트에 작은 상점을 연다. 상품 페이지를 붙이는 일은 짧지만, 돈과 재고를 다루기 시작하면 성공의 의미가 달라진다. 구매 버튼을 두 번 눌러도 주문은 한 번이어야 하고, 결제 응답을 잃어도 돈을 다시 청구해서는 안 된다.

## 1권의 애플리케이션을 이어받는다

이 권은 별도의 로그인 예제를 처음부터 만들지 않는다. accounts, content, 사용자 ID, 인증, 설정과 관측 기반을 유지하면서 catalog, inventory, cart, orders, payments, fulfillment를 추가한다. 기존 독자는 같은 계정으로 고객이 된다. 새 스키마와 배포가 기존 게시글 조회를 깨뜨리지 않는지도 회귀 테스트로 확인한다.

처음에는 모듈형 모놀리스다. 같은 데이터베이스 안에서 보장할 수 있는 트랜잭션부터 사용하고, 실제로 장애 격리와 독립 배포가 필요해질 때 배송 처리 하나를 분리한다. 마이크로서비스는 중급 개발자의 자격 요건이 아니라 비용을 설명해야 하는 선택이다.

## 이 권의 중심은 실패다

장바구니가 보낸 가격은 결제의 근거가 아니다. 상품 가격을 서버에서 다시 계산하고 주문 시점의 스냅샷을 저장한다. 마지막 재고를 여러 요청이 경쟁할 때는 데이터베이스의 원자적 갱신과 제약을 사용한다. Redis 락 하나로 모든 저장소와 결제사의 정합성이 해결되지는 않는다.

결제사, 메일 서비스, 브로커는 애플리케이션의 트랜잭션 밖에 있다. 타임아웃은 작업이 실행되지 않았다는 뜻이 아니다. 웹훅은 중복되거나 순서가 바뀔 수 있다. 이 권은 그런 조건에서 멱등성, 상태 전이, 대사, Outbox와 Inbox, 보상 작업을 설계한다.

CQRS와 Saga를 도입할 때도 실제 보장 범위를 분리한다. Fluo 패키지가 제공하는 디스패치·수명주기와 애플리케이션이 저장해야 하는 진행 상태는 다르다. 프로세스가 죽은 뒤 복구하는 책임을 메모리 이벤트 핸들러에 맡기지 않는다.

## 본문과 비교 실습

본문의 관계형 저장소는 PostgreSQL과 Prisma다. 배경 작업은 Redis 기반 큐로 시작하고 서비스 분리가 필요한 시점에 메시지 계약을 도입한다. 24장은 여러 전송 방식, 25장은 Drizzle, 26장은 Mongoose를 같은 요구와 테스트를 놓고 비교하는 실습이다. 모든 브로커와 ORM을 실행 앱에 동시에 추가하는 지시는 아니다.

실제 결제, 이메일, Slack과 Discord 전송은 외부 부작용이다. 책의 예제는 테스트 환경과 계약 대역, 운영 연결을 구분한다. 대역이 통과했다고 결제사나 배송사의 실제 연동 검증까지 끝났다고 주장하지 않는다.

## 완성 기준

정상적인 상품 조회와 구매만으로 이 권을 끝내지 않는다. 중복 웹훅, 큐 재전달, 결제사 응답 유실, 워커 중단, 예약 만료와 환불 실패를 재현하고 상태가 어떻게 수렴하는지 설명한다. 운영자가 어떤 지표와 기록으로 개입해야 하는지도 남긴다.

마지막에는 같은 주문 요청을 프레임워크 내부까지 따라갈 준비가 된다. 3권에서는 앞의 두 권에서 사용한 모듈과 요청이 어떻게 컴파일되고 해석되는지, 그리고 그 경계를 어떻게 확장하는지 살펴본다.
