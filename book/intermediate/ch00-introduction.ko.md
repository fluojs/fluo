# Introduction: Scaling Beyond the Monolith

fluo 시리즈의 중급편은 단일 애플리케이션에서 분산 시스템으로 넘어가는 경계부터 다룹니다.

초급편에서는 단일 인스턴스 애플리케이션을 견고하게 구성하는 데 집중했습니다. 표준 우선(Standard-First) 데코레이터 모델, 의존성 주입(DI), 기본 HTTP 레이어를 기준으로 서비스 경계를 정리했고, 엄격한 타입 안정성을 유지하면서 FluoShop의 초기 버전을 모듈형 모놀리스(Modular Monolith)로 구축했습니다.

중급편의 초점은 웹 서버 기초를 넘어 시스템 설계의 비용과 책임을 다루는 데 있습니다. 데이터 로컬리티(Data Locality), 네트워크 파티션, 서비스 디스커버리(Service Discovery)는 더 이상 부수적인 주제가 아닙니다. 모놀리스에서는 단일 데이터베이스와 로컬 트랜잭션이 일관성을 상당 부분 보장하지만, 분산 시스템에서는 로컬 함수 호출을 네트워크 메시지로 바꿔 생각해야 하며 최종 일관성(Eventual Consistency)을 명시적인 설계 조건으로 받아들여야 합니다.

## The Intermediate Journey

이 책의 목표는 fluo를 사용해 모듈형 모놀리스에서 확장 가능하고 회복력 있는 마이크로서비스 아키텍처로 전환하는 과정을 구체적으로 보여주는 것입니다. 이론 설명에 그치지 않고 FluoShop을 여러 서비스, 프로토콜, 런타임에 걸친 분산 시스템으로 단계적으로 리팩터링합니다. 우리는 네 가지 주요 테마에 집중합니다.

1. **마이크로서비스 인프라**: 트랜스포트 프로토콜, 메시지 패턴, 그리고 fluo가 어떻게 네트워크 복잡성을 추상화하는지 이해합니다 (TCP, Redis, RabbitMQ, Kafka, NATS, MQTT, gRPC).

2. **이벤트 기반 아키텍처**: 직접적인 요청 방식에서 벗어나 CQRS와 메시지 브로커를 활용한 디커플링된 이벤트 흐름으로 이동합니다.

3. **실시간 통신**: WebSocket 게이트웨이와 특화된 알림 시스템을 통해 요청-응답 모델을 넘어 확장합니다.

4. **플랫폼 이식성**: fluo의 통합 파사드(Facade)를 활용하여 Node.js, Bun, Deno, 그리고 에지(Edge) 환경(Cloudflare Workers)에서 로직을 실행합니다.

## The Evolution of FluoShop

이 책에서 FluoShop은 단순한 상점 애플리케이션에서 분산 시스템으로 확장됩니다. 시스템은 다음과 같은 책임별 서비스로 분리됩니다.

- **API 게이트웨이**: 데이터 집계와 횡단 관심사를 처리하는 진입점입니다.
- **카탈로그 서비스**: 고성능 읽기 경로에서 제품과 재고를 관리합니다.
- **주문 서비스**: 복잡한 비즈니스 워크플로와 상태 전이를 조율합니다.
- **결제 서비스**: 엄격한 실패 처리와 외부 연동이 필요한 고위험 도메인을 담당합니다.
- **알림 서비스**: Email, Slack, Discord 같은 여러 채널의 알림을 소비하고 발송합니다.

이 토폴로지를 기준으로 단순한 TCP부터 RabbitMQ, Kafka, NATS, MQTT 같은 브로커까지 여러 트랜스포트 프로토콜을 비교합니다. 핵심은 통일된 프로그래밍 모델입니다. 인프라를 바꿔도 비즈니스 핸들러의 의도와 구조가 유지되는지 확인합니다.

## Philosophy: Explicit Over Implicit

이 책 전반에서 fluo의 핵심 철학인 **명시성이 암시성보다 우선한다(Explicit Over Implicit)**는 원칙을 유지합니다.

분산 시스템은 본질적으로 복잡합니다. 여러 서비스와 메시지 브로커에 걸친 장애를 추적할 때 숨겨진 리플렉션(Reflection), 자동 탐색, 불투명한 메타데이터는 데이터와 의존성의 실제 흐름을 가립니다. 유지보수자는 편의 기능보다 관찰 가능한 경계를 더 필요로 합니다.

fluo에서 모든 것은 명시적인 프로바이더입니다. 의존성 그래프는 감사(Audit) 가능하고, 트랜스포트 설정은 코드에서 직접 확인할 수 있습니다. 명시성을 선택하면 약간의 보일러플레이트가 생기지만 예측 가능성과 유지보수성이 크게 좋아집니다. 이 책에서는 이벤트를 안정적으로 발행하기 위한 아웃박스(Outbox) 패턴과 네트워크 재시도로 발생하는 중복 메시지를 흡수하기 위한 멱등성 키도 함께 다룹니다.

## How to Navigate This Book

이 책은 분산 시스템을 도입할 때 실제로 마주치는 순서에 맞춰 구성되어 있습니다. 각 Part는 이전 결정 위에 다음 운영 문제를 얹는 방식으로 이어지므로, 독자는 FluoShop이 왜 그 시점에 새로운 트랜스포트나 패턴을 받아들이는지 자연스럽게 따라갈 수 있습니다.

- **Part 0. 마이크로서비스 준비**: 전략을 정의하고 첫 번째 트랜스포트로 TCP를 학습합니다.
- **Part 1. 메시지 브로커**: RabbitMQ, Kafka, NATS, MQTT, gRPC를 통합하고 각 트레이드오프를 평가합니다.
- **Part 2. 이벤트 기반 아키텍처**: 이벤트 버스, CQRS, Saga 패턴, 분산 잠금을 구현합니다.
- **Part 3. 실시간 통신**: 멀티 서비스 환경에서 WebSocket 게이트웨이와 Socket.IO를 확장합니다.
- **Part 4. 알림 시스템**: 이메일, 슬랙, 디스코드를 통해 알림을 오케스트레이션합니다.
- **Part 5. API 확장**: GraphQL과 Drizzle, Mongoose와 같은 현대적인 ORM을 탐구합니다.
- **Part 6. 플랫폼 이식성**: 동일한 비즈니스 로직을 Bun, Deno, Cloudflare Workers에 배포합니다.

## Setting Expectations

마이크로서비스는 만병통치약이 아닙니다. 네트워크 지연, 부분적 실패, 데이터 일관성, 운영 오버헤드 같은 비용을 새로 가져옵니다. 이 책은 그 비용을 숨기지 않습니다. 마이크로서비스를 사용하지 *말아야* 할 때, "분산된 모놀리스(Distributed Monolith)"의 함정, 아키텍처가 의도적인 트레이드오프의 연속이라는 사실을 함께 다룹니다.

## Community and Support

질문, 설계 논의, 피드백은 [GitHub Discussions](https://github.com/fluojs/fluo/discussions)와 Discord 커뮤니티에서 이어갈 수 있습니다. 실제 사용자의 문제와 제안이 fluo의 방향을 더 정확하게 만듭니다. fluo는 이 전환을 명시적으로 다루기 위해 설계되었습니다. 1장에서는 모놀리스를 어떤 기준으로 나눌지부터 정리합니다.

## 용어 사전

- **트랜스포트(Transport)**: 통신에 사용되는 기저 프로토콜(TCP, Kafka 등).
- **메시지 패턴(Message Pattern)**: 요청-응답 상호작용을 위한 고유 식별자.
- **이벤트 패턴(Event Pattern)**: 화이어-앤-포겟(Fire-and-forget) 브로드캐스트를 위한 고유 식별자.
- **클라이언트 프록시(Client Proxy)**: 원격 서비스로 메시지나 이벤트를 보내기 위해 사용하는 fluo 컴포넌트.
- **파사드(Facade)**: 서로 다른 런타임(Node, Bun, Edge)의 복잡성을 숨기는 추상화 레이어.

이 용어들은 fluo 마이크로서비스 생태계를 설명하는 공통 언어입니다. 이제 아키텍처 경계부터 살펴봅니다.

FluoShop은 단일 애플리케이션에서 분산 시스템으로 자연스럽게 진화합니다. 모듈형 모놀리스의 장점을 유지하면서 서비스 경계를 더 분명하게 나눌 것입니다. 중급편은 처음부터 마이크로서비스를 강요하지 않습니다. 먼저 왜 분리가 필요한지 설명합니다. 각 장은 아키텍처 결정을 FluoShop의 실제 변화와 연결합니다. 서비스 분해는 코드를 옮기는 일이 아니라 책임 경계를 정의하는 일에서 시작합니다. 카탈로그, 주문, 결제, 알림은 실패 모델이 서로 다른 도메인입니다. 네트워크 호출을 함수 호출처럼 착각하지 않는 법을 배웁니다.

데이터 로컬리티와 서비스 소유권은 분산 시스템 설계의 핵심입니다. 최종 일관성은 포기라기보다 설계 선택에 가깝습니다. FluoShop의 진화는 v0.0에서 더 큰 운영 현실로 나아가는 여정입니다. API 게이트웨이는 진입점이지만 모든 비즈니스 규칙을 소유하지는 않습니다. 카탈로그 서비스는 읽기 중심 워크로드에 맞는 모델을 보여줍니다. 주문 서비스는 장기 실행 흐름과 상태 전이를 주로 담당합니다. 결제 서비스는 외부 시스템 연동과 실패 복구 사이의 긴장을 드러냅니다. 알림 서비스는 반응형 소비자 모델의 가치를 보여줍니다.

TCP는 가장 단순한 출발점이며 서비스 간 메시징의 본질을 드러냅니다. Redis를 통해 빠른 이벤트 전달과 스트림 기반 내구성을 비교합니다. RabbitMQ는 큐 토폴로지와 라우팅 전략을 명시적으로 보여줍니다. Kafka는 재생, 파티셔닝, 소비자 그룹 같은 운영 개념을 소개합니다. NATS는 낮은 지연과 단순한 운영 모델이 중요한 지점을 보여줍니다. MQTT로는 텔레메트리와 장치 친화적인 메시징 시나리오를 다룹니다. gRPC는 명시적인 계약과 스트리밍 모델을 살펴볼 좋은 기회입니다. 같은 비즈니스 흐름이 서로 다른 트랜스포트 위에서 어떻게 표현되는지 비교할 것입니다.

트랜스포트가 바뀌어도 애플리케이션의 의도가 유지되는 것은 fluo의 중요한 약속입니다. 명시적 설정은 분산 환경에서 디버깅 시간을 줄여 줍니다. 숨겨진 메타데이터보다 드러난 프로바이더 구성이 더 신뢰할 만합니다. 서비스 디스커버리는 단순한 편의 기능이 아니라 시스템 신뢰성의 일부입니다. 네트워크 파티션은 예외 상황이 아니라 모든 분산 시스템이 언젠가 마주할 현실입니다. 재시도, 타임아웃, 멱등성을 함께 생각하는 습관을 기를 것입니다.

아웃박스 패턴은 이벤트 발행과 상태 변경을 더 안전하게 연결합니다. 도메인 이벤트는 단순한 알림이 아니라 비즈니스 사실의 기록입니다. 주문 하나가 생성되면서 여러 후속 흐름이 시작될 때 도메인 이벤트의 힘이 분명해집니다. 이벤트 기반 설계는 결합도를 낮추지만 관찰 가능성에 대한 요구를 높입니다. CQRS는 읽기 모델과 쓰기 모델을 억지로 같게 만들지 않도록 도와줍니다. 명령과 조회를 분리하면 서비스의 책임이 더 명확해집니다. 읽기 모델은 사용자 화면과 검색 경험에 맞춰 진화할 수 있습니다.

쓰기 모델은 무결성과 비즈니스 규칙을 중심에 둡니다. Saga는 여러 서비스에 걸친 긴 흐름을 하나의 일관된 프로세스로 이해하게 해줍니다. 보상 작업은 분산 트랜잭션의 현실적인 대안입니다. 장기 실행 주문 처리에서 Saga는 실패를 설계의 일부로 다룹니다. 이벤트 버스는 단순한 전파 도구가 아니라 경계 너머로 의미를 전달하는 장치입니다. 백그라운드 작업과 큐는 사용자 응답 시간을 보호하는 데 큰 역할을 합니다. 스케줄링과 분산 잠금에서는 운영 자동화를 지탱하는 안전장치를 다룹니다.

실시간 시스템으로 넘어가면 요청-응답만으로는 충분하지 않다는 사실이 분명해집니다. WebSocket 게이트웨이는 장바구니 변경, 주문 상태, 운영 알림을 더 즉시 전달합니다. Socket.IO를 통해 더 풍부한 상호작용과 룸 기반 시나리오를 살펴봅니다. 실시간 연결에서는 연결 수명 주기와 하트비트도 설계해야 합니다. FluoShop 지원 채널은 실시간 메시징이 서비스 경험을 어떻게 바꾸는지 보여줍니다. 알림 시스템은 이메일, Slack, Discord 같은 채널을 하나의 흐름으로 묶습니다. 사용자 알림과 운영 알림은 비슷해 보여도 우선순위와 실패 비용이 다릅니다. 이메일은 비동기 처리, 템플릿, 상태 추적의 중요성을 드러냅니다.

Slack 통합은 운영 팀이 이벤트를 즉시 파악하도록 돕습니다. Discord 통합은 커뮤니티와 지원 흐름을 더 긴밀하게 연결합니다. 알림 오케스트레이션은 채널별 구현을 공통된 의도 아래 모읍니다. GraphQL은 집계된 읽기 경험을 더 유연하게 설계하도록 돕습니다. REST와 GraphQL을 경쟁 관계가 아니라 상황에 따라 선택하는 도구로 보는 시각이 중요합니다. Mongoose는 문서 지향 모델링이 잘 맞는 사례를 보여줍니다. Drizzle을 통해 SQL 중심 사고와 타입 안정성을 함께 살펴봅니다. ORM 선택은 취향보다 데이터 접근 패턴과 팀 운영 방식에 관한 문제입니다.

같은 FluoShop 안에서도 저장소 기술에 따라 읽기 전략은 달라질 수 있습니다. 런타임 이식성은 모든 것을 특정 서버에 묶지 않는 설계를 가능하게 합니다. Node.js, Bun, Deno, Cloudflare Workers의 차이를 직접 경험하게 될 것입니다. 플랫폼 어댑터의 차이를 안다고 해서 비즈니스 로직을 다시 작성할 필요는 없습니다. 통합 파사드는 런타임 차이를 완전히 숨기는 대신 관리 가능한 경계로 바꿉니다. 중급편은 기능을 추가하는 데 그치지 않고 운영 판단력을 기르는 과정이기도 합니다. 로그, 메트릭, 실패 경로를 아키텍처 이야기의 일부로 다룰 것입니다.

분산 시스템에서 정상 경로만 설명하는 문서는 가장 위험합니다. 이 책은 성공 경로와 실패 경로를 함께 보여주려 합니다. 서비스를 나누는 이유가 팀 구조와 배포 전략에도 이어진다는 점을 살펴봅니다. 작은 모놀리스에서 출발하기 때문에 이후의 분해 과정이 더 설득력 있게 다가올 것입니다. 분산 아키텍처는 규모만을 위한 선택이 아니라 팀의 책임을 분리하는 방법이기도 합니다. 그럼에도 언제 모놀리스를 유지해야 하는지 솔직하게 이야기할 것입니다. 분산 모놀리스의 함정을 이해하면 성급한 분리를 피할 수 있습니다.

모든 서비스 경계에는 장점과 비용이 함께 존재합니다. 표준 우선 철학은 분산 환경에서도 여전히 중심 원칙입니다. 서비스 수가 늘어날수록 명시적 DI의 가치는 더 커집니다. 감사 가능한 의존성 그래프는 운영 사고를 분석하는 데도 도움이 됩니다. 중급편의 목표는 더 복잡한 시스템을 어렵지 않게 바라보도록 돕는 것입니다. 복잡성은 숨길 대상이 아니라 이해 가능한 조각으로 나눌 대상입니다. 각 장에서 새로운 인프라를 소개하기 전에 왜 필요한지부터 분명히 할 것입니다.

기술 선택은 유행이 아니라 문제 적합성을 따라야 합니다. Kafka를 사용한다고 시스템이 자동으로 더 성숙해지는 것은 아닙니다. NATS나 Redis가 더 적합한 순간도 분명히 있습니다. TCP처럼 단순한 출발점은 추상화 아래에 있는 실제 비용을 드러냅니다. gRPC의 계약 중심 접근은 팀 간 협업에도 도움이 될 수 있습니다. MQTT는 웹 백엔드를 넘어 연결된 장치의 세계를 생각하게 합니다. 실시간 업데이트는 사용자 만족도를 높이지만 운영 복잡성도 함께 가져옵니다. 알림 채널이 늘어날수록 중복 로직보다 공통 오케스트레이션이 중요해집니다.

CQRS와 이벤트 모델은 검색, 분석, 대시보드 경험을 더 유연하게 만듭니다. Saga를 이해하면 결제 실패와 재고 복구 흐름을 더 침착하게 설계할 수 있습니다. 잘 정의된 도메인 이벤트는 팀 간 대화도 더 정확하게 만듭니다. GraphQL 계층은 여러 서비스의 데이터를 모아 읽기 경험을 다듬는 데 유용합니다. Mongoose와 Drizzle을 비교하면 데이터 모델링 철학의 차이도 드러납니다. 런타임 이식성은 미래의 배포 전략 변화에 대비하는 보험입니다. 같은 핵심 로직을 여러 어댑터에서 실행하면 시스템에 대한 확신을 얻을 수 있습니다. 중급편을 마칠 때쯤이면 분산 애플리케이션의 언어가 익숙해질 것입니다.

트랜스포트, 이벤트, 큐, 실시간 연결을 하나의 시스템을 이루는 요소로 읽게 될 것입니다. FluoShop의 다음 변화가 왜 필요한지 설명할 수 있게 됩니다. 어려운 개념을 한 번에 모두 이해하지 못해도 괜찮습니다. 중요한 것은 각 장에서 시스템 사고의 폭을 조금씩 넓히는 일입니다. 질문이 생기면 함께 논의할 커뮤니티와 실험할 코드, 다시 읽을 예제가 있습니다. 초급편에서 이미 기초를 쌓았고, 이제 더 넓은 설계 공간으로 들어갑니다. 분산 시스템은 어렵지만 배울 수 있으며, fluo는 그 학습을 돕도록 설계되었습니다.

이제 FluoShop과 함께 다음 단계로 나아갈 시간입니다.
