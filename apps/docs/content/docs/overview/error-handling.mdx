## Exercise the three outcomes

Restart `pnpm dev` and run:

```bash
curl -i http://localhost:3000/posts/1
curl -i http://localhost:3000/posts/does-not-exist
curl -i -X POST http://localhost:3000/posts \
  -H 'content-type: application/json' \
  -d '{"title":"Hi","content":"Too short"}'
```

Expect `200`, `404`, and `400`, respectively.

The missing-record response has the framework's error envelope:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Post does-not-exist was not found.",
    "status": 404
  }
}
```

An application may also provide a request ID. Tests should assert the stable
machine fields relevant to the contract, not incidental object formatting.

## Unexpected errors are different

Unknown exceptions become server errors without exposing their original message
to clients. Do not catch every error and return `200` with an error-shaped
object: callers would lose the HTTP failure signal. Do not return stack traces,
database errors or connection details in public responses.

A route miss is also `404`, but it means no handler matched the method and path,
not that `PostsService` failed to find a record. Preserve that distinction when
debugging.
