You now have one application with modules, an injected service, input validation,
response shaping and intentional errors. Tests should exercise those boundaries
together, not only call controller methods in isolation.

Continue after [Error handling](/docs/overview/error-handling). Keep the tests
generated by the CLI: they still protect configuration, greeting and health.

## Add a request-level test

Create `test/posts.e2e.test.ts` in your generated project:

```ts title="test/posts.e2e.test.ts"
import { Test } from '@fluojs/testing';
import { expect, it } from 'vitest';
import { AppModule } from '../src/app';

it('creates, reads and protects the public post shape', async () => {
  const app = await Test.createApp({ rootModule: AppModule });
  try {
    const created = await app.request('POST', '/posts')
      .body({ title: 'Second post', content: 'Created through HTTP' }).send();
    expect(created.status).toBe(201);
    expect(created.body).toEqual({
      id: '2',
      title: 'Second post',
      content: 'Created through HTTP',
    });

    const found = await app.request('GET', '/posts/2').send();
    expect(found.status).toBe(200);
    expect(found.body).toEqual(created.body);

    const invalid = await app.request('POST', '/posts')
      .body({ title: 'Hi', content: 'Rejected' }).send();
    expect(invalid.status).toBe(400);

    const missing = await app.request('GET', '/posts/missing').send();
    expect(missing.status).toBe(404);
    expect(missing.body).toMatchObject({
      error: { code: 'NOT_FOUND', status: 404 },
    });

    const listed = await app.request('GET', '/posts').send();
    expect(listed.status).toBe(200);
    expect(listed.body).toHaveLength(2);
  } finally {
    await app.close();
  }
});
```

`Test.createApp` assembles the real module graph and dispatches requests through
the HTTP pipeline. Exact response equality also catches accidentally exposed
fields such as `internalNotes`. The final list assertion proves rejected input
did not mutate the collection.

Each test creates and closes its own application. Do not share mutable posts
state across tests or depend on test execution order. Close in `finally` so a
failed assertion does not leave resources alive.

## Run the whole suite

```bash
pnpm test
```

Keep the generated Vitest decorator configuration. Do not replace it with a
plain TypeScript transform or add legacy decorator flags to solve a test failure.

If the posts test returns a route-miss `404`, first check that `PostsModule` is
imported by the generated `AppModule`. If bootstrap reports an unresolved
dependency, check `providers` and the controller's `@Inject` token.

## Prove the production path

Stop `pnpm dev` before starting another listener on the same port:

```bash
pnpm build
pnpm start
```

In another terminal, check the preserved starter endpoints and the new feature:

```bash
curl -i http://localhost:3000/health
curl -i http://localhost:3000/ready
curl -i http://localhost:3000/greeting
curl -i http://localhost:3000/posts
curl -i http://localhost:3000/posts/1
```

All return `200`. A fresh process contains only the seed post; posts created
during development are not persisted. Stop the server with Ctrl+C when done.

Request tests and a listener smoke test prove different things. The first
checks application behavior deterministically; the second checks that the
built entrypoint starts and accepts real HTTP traffic.

## What you have completed

- The generated root still owns configuration, greeting and health.
- `PostsModule` owns its controller and service.
- `@Inject` makes the controller dependency explicit.
- DTO binding and validation reject invalid input before mutation.
- Response DTOs and `SerializerInterceptor` keep internal fields private.
- Missing resources return a structured `404`.
- Tests exercise the complete request path and production startup.
