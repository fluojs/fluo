Data packages keep storage semantics explicit instead of hiding every database behind one abstraction.

| Package | Use for | Deep dive |
| --- | --- | --- |
| `@fluojs/prisma` | Prisma clients and transaction context | `packages/prisma/README.md` |
| `@fluojs/drizzle` | Drizzle database lifecycle and transactions | `packages/drizzle/README.md` |
| `@fluojs/mongoose` | Mongoose connections, sessions, request transactions | `packages/mongoose/README.md` |
| `@fluojs/redis` | Redis clients and named clients | `packages/redis/README.md` |

| `@fluojs/queue` | Redis-backed jobs and workers | `packages/queue/README.md` |

Read [Persistence](../guides/persistence) when choosing a storage path for an application feature.

For a queue-free cache increment or another pure single-key mutation, use [`CacheService.update`](https://github.com/fluojs/fluo/blob/main/packages/cache-manager/README.md#atomic-updates), not a `get`/`set` pair. The package README owns the set/delete decision, fixed-expiry TTL, retry/error contract, and optional store capability. Memory coordinates one shared store instance; Redis requires explicit cache-side `redis.atomicUpdates: true` through the canonical RedisModule DI path and the owner's single-primary/namespace prerequisites. This does not add a RedisService API, provide a database transaction, or change `remember` loader coalescing. See [Operations](../guides/operations#cache-update-drain) for drain and metadata considerations.

Prisma, Drizzle, and Mongoose `afterCommit` can register cache invalidation after native commit. [After-commit cache invalidation](../guides/persistence#after-commit-cache-invalidation) explains `requireAfterCommit` preflight and the already-committed `AfterCommitError`. `docs/architecture/transactions.md` owns execution semantics and the package READMEs above own public APIs. This does not include Redis commit tracking, DB+Redis atomicity, a durable outbox, or crash/network exactly-once guarantees.
