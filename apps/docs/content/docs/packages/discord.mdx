title: Discord
description: Webhook-first Discord delivery with configurable retry policy, thread routing, template fallbacks, and a notifications channel.
package: "@fluojs/discord"
---

`@fluojs/discord` sends Discord messages through a transport you inject. The
built-in helper posts to an incoming webhook over any fetch-compatible HTTP
boundary and supports thread routing; bot-backed REST delivery implements the
exported `DiscordTransport` contract instead. An application injects
`DiscordService` for direct delivery, and `DISCORD_CHANNEL` lets
[`@fluojs/notifications`](/docs/packages/notifications) route dispatches into
Discord alongside [`@fluojs/email`](/docs/packages/email) and
[`@fluojs/slack`](/docs/packages/slack).

The module API matches its siblings on purpose: global-by-default
registration, `inject` + `useFactory` async registration, lifecycle-gated
sends, capability-based bootstrap verification, and no `process.env` reads.
Unlike Slack, the webhook transport exposes a **configurable retry policy**
(`attempts` 1-10, `baseDelayMs` 0-60000) and routes messages into threads via
`thread_id`. Use it when Discord is one of several notification channels or
when delivery must stay portable across runtimes. Do not expect a Discord SDK:
there is no gateway/WebSocket client, no slash-command registry, no
multi-client surface, and one notification dispatch never fans out to several
threads implicitly.

## Installation

```bash
npm install @fluojs/discord @fluojs/notifications
```

The package supports Node.js `>=24.0.0 <27` as its package-owned support
contract; the delivery boundary itself stays transport-agnostic at runtime
through the injected fetch-compatible `fetch`.

## A small working example

A release announcer that posts into a release thread. Three declarations:
the transport, the module registration, and the sender.

```ts title="src/release-notifier.ts"
import { Inject } from '@fluojs/core';
import { DiscordService } from '@fluojs/discord';

@Inject(DiscordService)
export class ReleaseNotifier {
  constructor(private readonly discord: DiscordService) {}

  async announce(version: string): Promise<void> {
    const result = await this.discord.send({
      content: `Deploy ${version} finished successfully.`,
      embeds: [{ description: 'Build 124 succeeded.', title: 'Release report' }],
    });

    // The webhook's wait=true default lets Discord echo back the created
    // message, so result.messageId/threadId are real ids, not guesses.
    if (!result.ok) {
      throw new Error(`Discord announcement for ${version} failed`);
    }
  }
}
```

```ts title="src/app.module.ts"
import { Module } from '@fluojs/core';
import { DiscordModule, createDiscordWebhookTransport } from '@fluojs/discord';

import { ReleaseNotifier } from './release-notifier';

// Resolved from your configuration layer - the package itself never reads
// process.env.
const discordWebhookUrl = 'https://discord.com/api/webhooks/123/abc';

@Module({
  imports: [
    DiscordModule.forRoot({
      defaultThreadId: 'release-thread-id',
      transport: createDiscordWebhookTransport({
        fetch: globalThis.fetch.bind(globalThis),
        retry: { attempts: 5, baseDelayMs: 500 },
        webhookUrl: discordWebhookUrl,
      }),
    }),
  ],
  providers: [ReleaseNotifier],
})
export class AppModule {}
```

`DiscordModule.forRoot(...)` exports `DiscordService`, `DiscordChannel`, and
`DISCORD_CHANNEL` **globally by default**; pass `global: false` to scope them
to importing modules. Expected outcome: `announce('v1.2.3')` POSTs one JSON
payload to the webhook (with `wait=true` and `thread_id` when a thread target
is set) and resolves with
`{ ok: true, statusCode: 200, messageId: '...', threadId: 'release-thread-id' }`.

## How the mechanics work

### The webhook transport: URL handling, threads, and retries

`createDiscordWebhookTransport(...)` validates its inputs up front: a
malformed or non-absolute `webhookUrl` rejects immediately with
`DiscordConfigurationError` instead of failing later as a delivery error, and
an invalid retry policy is rejected the same way. Each send appends
`wait` (default `true`) to the URL so Discord returns the created message,
plus `thread_id` when the message carries a `threadId` (direct) or resolves
one from `recipients` (notifications).

The retry policy is the package's distinguishing transport feature:

| Setting | Rules |
| --- | --- |
| `attempts` | Integer `1`-`10`; includes the initial request; default `3` |
| `baseDelayMs` | Integer `0`-`60000`; later waits double from the base; default `250` |
| What retries | Transient `408`, `429`, `5xx` responses and transport-level exceptions |
| What never retries | Permanent upstream statuses (bad payload, invalid webhook) |
| Cancellation | Backoff observes `DiscordSendOptions.signal`; an already-aborted signal rejects immediately |

Increase attempts for a latency-tolerant ops announcer; keep the default when
a request path depends on the send. The policy is bounded in-process retry -
it does not survive process restarts. When a notification must be durable,
queue it through [`@fluojs/notifications`](/docs/packages/notifications)
instead of inflating `attempts`.

Successful webhook responses are parsed so `DiscordSendResult` can expose
`channelId`, `guildId`, `messageId`, and the effective `threadId`; a non-JSON
success body is still a success with a `warnings` entry. Caller-visible
`DiscordTransportError` messages omit raw upstream response bodies by
default, including after exhausted rate-limit retries.

### Messages and validation

`send(...)` resolves `defaultThreadId` before delivery and validates that the
message has Discord-visible content - `content`, `embeds`, `components`,
`attachments`, or `poll` - rejecting empty messages with
`DiscordMessageValidationError`. Payload objects (embeds, components,
attachments, polls, `allowedMentions`) are forwarded opaquely; the package
does not interpret their fields.

`sendMany(...)` sends sequentially in input order and is fail-fast by
default; `continueOnError: true` collects a batch result. It is a
`DiscordMessage[]` batch API, not a multi-recipient dispatch shortcut.

### Lifecycle: readiness gating and shutdown

Sends are accepted only after bootstrap marks the transport `ready`. Attempts
before bootstrap, during startup, after failed bootstrap, while shutting down,
or after shutdown are rejected before delivery. During `onApplicationShutdown`
the service drains deliveries that were accepted while `ready` (a delivery
rejection stays the caller's result and does not fail shutdown), then closes
a factory-owned transport exactly once - including one still being created
when shutdown began. If bootstrap verification fails and the subsequent owned
cleanup also fails, status diagnostics preserve the first `initialization`
failure phase instead of reclassifying it as `shutdown-cleanup`.

`verifyOnModuleInit: true` awaits `transport.verify()` during `onModuleInit()`
when the transport exposes it. Verification is capability-based - the webhook
transport has no `verify()` and skips the step - so a bot-token transport can
fail startup on a bad token instead of failing the first announcement.

### Notifications: one dispatch, one thread

`Slack`-style recipient translation, Discord-shaped:

- `recipients[0]` (a thread id) is the target; with `recipients` omitted the
  configured `defaultThreadId` is used. Multiple recipients reject with
  `DiscordMessageValidationError` - fan out with `sendMany(...)` or separate
  dispatches.
- Supported payload fields: `content`, `embeds`, `components`, `attachments`,
  `allowedMentions`, `username`, `avatarUrl`, `tts`, `threadName`, `flags`,
  `poll`, `metadata`.
- An optional `DiscordTemplateRenderer` runs when both `notification.template`
  and a module renderer are present. The render input includes `signal`, so
  renderers can stop caller-cancelled work before transport delivery.
  Explicit `payload.content`/`embeds`/`components` beat rendered values; when
  `payload.content` is undefined, content falls back to rendered content and
  then to `notification.subject`.
- Metadata merges as payload metadata, dispatch metadata, then
  subject/template markers - on duplicate keys, dispatch metadata overrides
  payload metadata, and the final markers override both.

Register the channel exactly like the other leaf packages:

```ts title="fragment: registering the Discord channel"
import { NotificationsModule } from '@fluojs/notifications';
import { DISCORD_CHANNEL, DiscordModule } from '@fluojs/discord';

@Module({
  imports: [
    DiscordModule.forRoot({ /* transport wiring */ }),
    NotificationsModule.forRootAsync({
      inject: [DISCORD_CHANNEL],
      useFactory: (channel) => ({ channels: [channel] }),
    }),
  ],
})
export class AppModule {}
```

The channel name defaults to `discord`; rename it via
`notifications: { channel: ... }`. Blank `defaultThreadId` and blank channel
names are trimmed and ignored.

## Composition with neighboring packages

**With `@fluojs/notifications`.** `DISCORD_CHANNEL` is the whole integration
surface; application services dispatch envelopes and never import Discord
payload types.

**With `@fluojs/config`.** Resolve the webhook URL, thread id, and retry
policy in `forRootAsync({ inject: [ConfigService], useFactory })`. The async
shape is `inject` plus `useFactory` only - NestJS `imports`, `useClass`, and
`useExisting` are explicitly unsupported, and internal provider helpers or
option tokens are not exported to replace.

**With `@fluojs/queue`.** Webhook retries are bounded and in-process. For
announcements that must survive restarts or bursts, configure the
notifications foundation's queue seam (as the [email guide](/docs/packages/email)
shows for its built-in worker) and keep `attempts` small.

## Defaults, ownership, and lifecycle

| Concern | Default | Owner |
| --- | --- | --- |
| Module visibility | `global: true` | `forRoot({ global })` / `forRootAsync({ global })` |
| Webhook retry policy | 3 attempts, 250ms base | `retry` (validated 1-10 / 0-60000) |
| Webhook `wait` parameter | `true` (echoes the created message) | `wait: false` for fire-and-forget |
| Transport resources | Instance `false`, factory `true` | `transport.ownsResources` |
| Bootstrap verification | Off | `verifyOnModuleInit: true` + capability-based `verify()` |
| Notifications channel name | `'discord'` | `notifications.channel` |
| Fan-out | Never implicit | `sendMany(...)` or separate dispatches |

The webhook transport owns nothing; factory-owned transports close exactly
once during shutdown after accepted deliveries drain.
`createPlatformStatusSnapshot()` reports lifecycle state, bootstrap
verification state, distinct initialization vs shutdown-cleanup failure
diagnostics, transport kind/ownership, and default thread configuration.

## Failures, limits, and common mistakes

- **`DiscordConfigurationError`.** Empty or malformed `webhookUrl`, or an
  invalid retry policy (`attempts: 0`, `attempts: 11`, negative or oversized
  `baseDelayMs`). These fail fast at transport construction.
- **`DiscordMessageValidationError`.** A message with none of
  `content`/`embeds`/`components`/`attachments`/`poll`, or a notification
  dispatch with multiple recipients.
- **`DiscordTransportError` that "should have retried".** Only `408`, `429`,
  and `5xx` retry. A `404` (deleted webhook) or `400` (bad embed payload)
  fails on the first attempt by design - fix the payload or webhook.
- **`DiscordTransportError` during shutdown races.** There is no separate
  lifecycle error class here: sends that arrive while the service is stopping
  or stopped reject with `DiscordTransportError` ("Discord transport is
  shutting down or already stopped") before reusing the transport, and a
  failed bootstrap surfaces through the same type. Catch it where sends can
  race teardown.
- **Rate limits at high volume.** Discord rate limits aggressive webhook use
  regardless of client retry logic; queue high-volume announcement flows
  rather than raising `attempts`.
- **Private provider migration paths.** `createDiscordProviders(...)`,
  `DISCORD_OPTIONS`, and normalized option types are deliberately not
  exported. Wrap `DiscordModule.forRoot(...)` in an app-owned module when a
  NestJS migration previously customized provider internals.

## Testing

Inject a recording fetch and assert on the request - URL parameters included,
since thread routing lives there:

```ts title="fragment: webhook transport seam test"
const calls: Array<{ url: string; body: Record<string, unknown> }> = [];
const fetchLike: DiscordFetchLike = async (input, init) => {
  calls.push({ url: input, body: JSON.parse(init?.body ?? '{}') as Record<string, unknown> });
  return { ok: true, status: 200, text: async () => '{"id":"m1","channel_id":"c1"}' };
};

const transport = createDiscordWebhookTransport({
  fetch: fetchLike,
  retry: { attempts: 3, baseDelayMs: 0 },
  webhookUrl: 'https://discord.com/api/webhooks/123/abc',
});
const result = await transport.send(
  { attachments: [], components: [], embeds: [], content: 'Deploy finished', threadId: 't-9' },
  {},
);

expect(result.messageId).toBe('m1');
expect(calls[0]?.url).toContain('thread_id=t-9');
expect(calls[0]?.url).toContain('wait=true');
```

Setting `baseDelayMs: 0` makes retry-path tests deterministic without sleeps:
a fake fetch that answers `503`, `503`, then `200` exercises the full backoff
loop while the test asserts only call order and final results. At the module
level, register `DiscordModule.forRoot(...)` with the recording transport and
drive `DiscordService` through `Test.createApp(...)`, closing the app in
`finally`.
