## 목표와 시작 지점

[과정 소개](/ko/docs/tutorial)를 읽은 뒤 시작합니다. Git, Node.js `>=24.0.0 <27`, pnpm 10이 필요합니다. 이전 애플리케이션 체크포인트는 필요하지 않습니다.

목표는 health만 있는 학습 앱을 빌드하고 실행해 `/health`에서 `200`과 `{"status":"ok"}`를 받는 것입니다. 이 과정은 **Fluo 저장소 안의 예제**를 사용하므로 수업 소스, 의존성, 복구 스냅샷이 같은 checkout을 기준으로 합니다. 모든 수업에서 `examples/fluo-blog/00-start`를 수정합니다.

## 1. 하나의 workspace 준비하기

프로젝트를 둘 디렉터리에서 실행합니다.

```bash
git clone https://github.com/fluojs/fluo.git
cd fluo
node --version
pnpm --version
pnpm install
pnpm build
```

설치 전에 Node가 지원 범위에 있고 pnpm이 `10.x`를 출력하는지 확인하세요. 여기서 `pnpm build`는 저장소의 프레임워크 패키지를 빌드합니다. 예제의 `workspace:*` 의존성이 이 결과물을 사용하므로 의존성 설치만 성공했다고 빌드를 생략할 수는 없습니다.

**과정의 모든 명령은 이 저장소 루트에서 실행합니다.** 학습할 애플리케이션은 `examples/fluo-blog/`에 있습니다.

이번 수업에서는 소스 파일을 직접 추가하지 않습니다. clone한 저장소에 이후 수업에서 사용하는 파일이 이미 들어 있습니다.

```text
examples/fluo-blog/
  package.json
  tsconfig.json
  vite.config.ts
  vitest.config.ts
  00-start/
    src/
      app.ts
      main.ts
    test/
      app.e2e.test.ts
  01-first-route/
    src/
    test/
  02-dependency-injection/
    src/
    test/
  03-validation-errors/
    src/
    test/
```

직접 수정하는 디렉터리는 `00-start` 하나입니다. 처음에는 health 라우트와 테스트만 있고 posts 기능은 없습니다. 나머지 세 디렉터리는 완성된 복구 스냅샷이므로 수정하지 않습니다. 네 디렉터리는 패키지와 도구 설정을 공유합니다. 이후 수업에서 `00-start`에 소스와 테스트를 추가하며 자신의 앱을 누적해서 확장합니다.

## 2. 애플리케이션을 시작하는 파일 알아보기

| 파일 | 역할 |
| --- | --- |
| `00-start/src/app.ts` | `AppModule`을 export하고 starter health 라우트를 유지합니다. |
| `00-start/src/main.ts` | Static Fastify adapter와 `FluoFactory.create(...)`로 앱을 생성한 뒤 `app.listen()`을 await합니다. |
| `00-start/test/app.e2e.test.ts` | 요청 파이프라인으로 `/health`, `/ready`를 확인합니다. |
| `vite.config.ts` | 선택한 체크포인트를 `fluoDecoratorsPlugin()`과 `node24` 대상으로 빌드합니다. |
| `vitest.config.ts` | `@fluojs/testing/vitest`의 `fluoBabelDecoratorsPlugin()`으로 테스트를 실행합니다. |

`AppModule`은 `src/app.module.ts`가 아니라 <strong><code>src/app.ts</code></strong>에 있습니다. 루트 모듈은 애플리케이션을 조합하는 경계이며 `GET /` 라우트를 자동으로 만들지는 않습니다.

기본 health 라우트는 `AppModule.imports`의 `HealthModule.forRoot()`가 제공합니다. 과정 전체에서 이 import를 유지하세요. `/health`를 위한 컨트롤러를 중복으로 만들지 않습니다.

이 `repository-example`, 기본 CLI Node/Fastify 스타터, `examples/minimal`은 같은 Factory와 static adapter 경로를 사용합니다. 진입점은 Node logger와 shutdown callback을 명시적으로 선택하고 `app.listen()`을 한 번 await합니다. [Bootstrap 담당 문서](https://github.com/fluojs/fluo/blob/main/docs/getting-started/bootstrap-paths.ko.md)가 기본값, 실패 정리, 호스트 소유권을 정의합니다. Decorated declaration 평가 전에 metadata가 준비되도록 공통 표준 decorator build/test 설정을 유지합니다.

## 3. Fastify 시작하기

저장소 루트에서 실행합니다.

```bash
pnpm --filter @fluojs/example-fluo-blog build:00
pnpm --filter @fluojs/example-fluo-blog start:00
```

빌드가 성공한 뒤 서버를 시작해야 합니다. 서버 주소는 `http://127.0.0.1:3000`입니다. 서버를 켜 두고 두 번째 터미널을 엽니다.

```bash
curl -i http://127.0.0.1:3000/health
curl -i http://127.0.0.1:3000/ready
```

시작이 끝나면 두 응답의 상태 코드는 모두 `200`입니다. JSON 본문은 다음과 같습니다.

```json title="GET /health"
{"status":"ok"}
```

```json title="GET /ready"
{"status":"ready"}
```

기본 엔드포인트는 이 작은 앱이 살아 있고 요청을 받을 준비가 되었음을 보여줍니다. 예제에 존재하지 않는 데이터베이스의 상태까지 확인하지는 않습니다.

수정한 코드를 다시 빌드하기 전에 Ctrl+C로 프로세스를 종료하세요. `start:00`은 빌드된 `dist/00-start/main.js`를 실행하며 소스 변경을 감시하지 않습니다. 수정 후에는 종료, 재빌드, 재시작해야 합니다. 진입점에서 `PORT`로 `3000`을 변경할 수 있지만 과정의 모든 명령은 `3000`을 사용합니다. 단순히 `build`나 `start`를 사용하지 마세요. 그 package 별칭은 학습 앱이 아니라 완성 스냅샷을 실행합니다.

Checkpoint의 `PORT` 변환은 `Number(process.env.PORT ?? '3000')`이며 CLI의 `parseInt`/non-finite fallback은 없습니다. Fastify는 결과 숫자를 검증하고 정수 port `0..65535`를 허용합니다. Book의 더 엄격한 10진수 `1..65535` parser는 애플리케이션 정책이며 이 수정하지 않은 checkpoint의 동작이 아닙니다.

저장소 루트에서 초기 health 테스트를 실행합니다.

```bash
pnpm --filter @fluojs/example-fluo-blog exec vitest run 00-start
```

health/readiness 두 사례가 모두 통과해야 합니다. 다음 수업에서는 이 검증을 삭제하지 않고 같은 테스트 파일을 확장합니다.

## 외부 CLI 앱 명령과 다른 이유

배포된 CLI의 기본 Node/Fastify starter는 별도의 시작 환경입니다. 생성된 `src/app.ts`에는 `ConfigModule`, `GreetingModule`, `HealthModule.forRoot()`가 있고, `src/`의 greeting 테스트와 `test/app.e2e.test.ts`도 있습니다. 저장소 예제는 같은 공개 모듈·bootstrap 모델을 사용하지만 greeting 없이 posts와 health만 담고 있습니다.

생성 앱의 `app.ts`를 예제 파일로 통째로 덮어쓰고 starter 테스트를 그대로 남기지 **마세요**. 그러면 greeting 등록은 없어지는데 테스트는 여전히 greeting을 기대합니다. 생성 앱에 posts 기능을 추가할 때는 기존 `AppModule`의 config, greeting, health import와 테스트를 유지해야 합니다. 이 과정의 전체 파일 교체 지시는 `examples/fluo-blog/00-start`만 대상으로 합니다.

workspace 필터, 번호별 빌드 스크립트, `workspace:*` 의존성 버전, mode 기반 Vite 설정은 저장소 전용입니다. 외부 생성 앱은 자신의 package 스크립트와 registry 의존성을 사용합니다. 이 과정은 저장소의 다음 패키지 버전이 이미 배포되었다고 가정하지 않습니다. 과정을 마친 후 별도 앱을 만들려면 [빠른 시작](/ko/docs/getting-started/quick-start)의 배포 CLI 안내를 따르세요. 그 작업 디렉터리와 이 과정의 디렉터리를 섞지 마세요.

## 복구

[시작 앱 완성본](https://github.com/fluojs/fluo/tree/main/examples/fluo-blog/00-start)과 [예제 공통 설정](https://github.com/fluojs/fluo/tree/main/examples/fluo-blog)을 사용하세요. 이후 복구 스냅샷도 `00-start` 안의 해당 파일을 교체할 때 쓰는 기준이지 실행 앱을 바꾸라는 뜻이 아닙니다.

| 증상 | 조치 |
| --- | --- |
| workspace 필터가 패키지를 찾지 못함 | clone한 저장소 루트에서 실행하는지, 현재 checkout에 `examples/fluo-blog/package.json`이 있는지 확인합니다. |
| 프레임워크 패키지의 빌드 진입점이 없음 | 체크포인트 빌드 전에 루트 `pnpm install`과 `pnpm build`를 완료합니다. |
| 연결 거부 | `start:00`을 실행한 상태로 시작이 끝난 뒤 `127.0.0.1:3000`에 요청합니다. |
| 포트가 이미 사용 중임 | 학습 앱을 다시 시작하기 전에 이전 과정 서버를 종료합니다. |
| `/health`가 `404`를 반환함 | 체크포인트의 `src/app.ts`와 비교하고 `HealthModule.forRoot()` 등록을 유지합니다. |
