## 목표와 이전 체크포인트

[기능 전체 테스트](/ko/docs/tutorial/testing)를 마친 뒤 시작합니다. 직접 수정하는 앱은 여전히 `examples/fluo-blog/00-start`이며 애플리케이션 소스는 이제 `03-validation-errors` 복구 스냅샷과 같습니다.

이 수업에서는 **파일을 추가하거나 교체하지 않습니다**. 목표는 최종 상태를 검증하고 제공하지 않는 기능을 이해하며, 튜토리얼을 production 애플리케이션으로 오해하지 않고 다음 가이드로 연결하는 것입니다.

## 참조 스냅샷이 아닌 자신의 앱 검증하기

Ctrl+C로 이전 서버를 종료합니다. 저장소 루트에서 실행하세요.

```bash
pnpm --filter @fluojs/example-fluo-blog exec vitest run 00-start
pnpm --filter @fluojs/example-fluo-blog typecheck
pnpm --filter @fluojs/example-fluo-blog build:00
pnpm --filter @fluojs/example-fluo-blog start:00
```

테스트와 typecheck가 통과하고 빌드가 성공한 뒤 서버가 시작되어야 합니다. 계속 명시적인 `:00` 스크립트를 사용하세요. package의 단순 `build`, `start` 별칭은 완성된 참조 스냅샷을 실행합니다.

두 번째 터미널에서 실행합니다.

```bash
curl -i http://127.0.0.1:3000/health
curl -i http://127.0.0.1:3000/ready
curl -i http://127.0.0.1:3000/posts
curl -i http://127.0.0.1:3000/posts/2
```

새로 시작한 프로세스의 결과입니다.

| 요청 | 상태 코드 | 본문 |
| --- | --- | --- |
| `/health` | `200` | `{"status":"ok"}` |
| `/ready` | `200` | `{"status":"ready"}` |
| `/posts` | `200` | `[{"id":"1","title":"Hello, Fluo!","content":"My first post."}]` |
| `/posts/2` | `404` | `{"error":{"code":"NOT_FOUND","message":"Post 2 was not found.","status":404}}` |

오류에는 `requestId`가 추가될 수 있습니다. 프로세스를 재시작했으므로 이전 수업의 게시글 `2`는 사라졌습니다. 테스트도 이 서버의 데이터를 채우지 않습니다. 각 테스트 애플리케이션은 별도의 상태를 소유합니다.

## 배운 내용

컨트롤러를 만들고 처음에는 `AppModule`에, 이후에는 `PostsModule`에 등록했습니다. 클래스 수준의 `@Inject`로 서비스를 전달하고 DTO로 URL과 body 필드를 바인딩했으며 요청 파이프라인에서 HTTP 상태·본문 계약을 검증했습니다.

완성 앱은 `GET /posts`, `GET /posts/:id`, `POST /posts`와 유지된 health/readiness 라우트를 지원합니다. 수정·삭제 라우트, 브라우저 UI, 사용자, 영속 저장소, 배포는 제공하지 않습니다.

## 재시작 후에도 게시글 유지하기

[영속성](/ko/docs/guides/persistence)으로 이어갑니다. 서비스의 배열에서 저장 책임을 옮기되 컨트롤러와 요청 테스트는 공개 동작 계약으로 유지하세요. 영속성 가이드는 패키지별 데이터베이스와 연결 수명주기 계약을 설명합니다.

다음 확인 기준은 구체적입니다. 게시글을 생성하고 프로세스를 재시작한 뒤에도 조회에 성공해야 합니다. 데이터베이스 스키마, migration, ID 생성, 연결 종료, 트랜잭션 경계는 다음 구현의 범위입니다. 이 과정의 메모리 배열과 순차 ID는 이를 해결하지 않습니다.

## 게시글 생성 권한 정하기

[인증](/ko/docs/guides/auth)으로 이어갑니다. 현재는 서버에 접근할 수 있는 누구나 게시글을 생성할 수 있습니다. DTO 검증은 입력 형태를 검사할 뿐 호출자를 인증하거나 작업을 인가하지 않습니다.

게시글 소유자를 정의하고 적절한 guard/strategy로 생성을 보호하며 익명·인증·금지 요청을 테스트하세요. 들어온 사용자 ID를 신원 증명으로 취급하지 말고 인증 가이드의 실제 JWT와 Passport 계약을 따릅니다.

## starter의 운영 가정 확장하기

[운영](/ko/docs/guides/operations)과 [Production 체크리스트](/ko/docs/operations/production-checklist)로 이어갑니다.

현재 `/health`와 `/ready`는 데이터베이스나 외부 서비스를 검사하지 않습니다. 해당 의존성이 생기면 애플리케이션에 맞는 readiness 검사, 종료 동작, 설정, 로그, 지표, 리소스 한도를 설계해야 합니다. starter health 모듈을 다른 health 제공자로 바꿀 때는 같은 경로에 경쟁하는 라우트를 등록하지 마세요.

이 과정의 테스트 통과는 튜토리얼 계약이 동작한다는 근거입니다. 공개 production 배포 준비가 끝났다는 근거는 아닙니다.

## 같은 테스트 습관으로 확장하기

provider override와 더 넓은 요청 검증은 [테스트](/ko/docs/guides/testing), 라우트와 파이프라인 기능은 [HTTP API](/ko/docs/guides/http-api), 더 큰 입력·출력 경계는 [검증과 직렬화](/ko/docs/guides/validation-serialization)를 참고하세요.

새 동작마다 먼저 실패하는 동작 테스트를 만들고 이를 통과하는 최소 변경을 적용합니다. DTO와 오류 테스트는 실제 요청 경로를 유지하며 `finally`에서 정리하세요.
