## 목표와 이전 체크포인트

[의존성 주입](/ko/docs/tutorial/dependency-injection)을 마친 뒤 시작합니다. 체크포인트 02는 게시글 목록과 ID 조회를 제공하며 없는 ID에는 리소스 오류를 반환합니다.

이제 `examples/fluo-blog/00-start`에서 작업합니다. `src/create-post.dto.ts`를 추가하고 `src/posts.controller.ts`, `src/posts.service.ts`를 교체합니다. `src/post.ts`, `src/post-params.dto.ts`, `src/posts.module.ts`, `src/app.ts`, `src/main.ts`는 체크포인트 02에서 유지합니다. 새 라우트의 연결을 빠뜨리지 않도록 전체 루트 등록 코드도 다시 제시합니다.

확인할 목표는 올바른 JSON이 `201`로 게시글 `2`를 생성하고, 잘못된 제목은 아무것도 생성하지 않은 채 `400`을 반환하며, `/posts/999`는 계속 `404`를 반환하는 것입니다.

## 1. 입력 정의와 바인딩 연결하기

예제는 이미 `@fluojs/validation`을 workspace 의존성으로 선언합니다. [앱 만들기](/ko/docs/tutorial/create-app)의 루트 설치가 이를 준비하므로 임의의 registry 버전을 추가하지 않습니다.

{/* fluo-tutorial-source: examples/fluo-blog/03-validation-errors/src/create-post.dto.ts */}
```ts title="00-start/src/create-post.dto.ts"
import { FromBody } from '@fluojs/http';
import { IsDefined, IsString, MaxLength, MinLength } from '@fluojs/validation';

export class CreatePostDto {
  @FromBody()
  @IsDefined()
  @IsString()
  @MinLength(3)
  @MaxLength(120)
  title = '';

  @FromBody()
  @IsDefined()
  @IsString()
  @MinLength(1)
  @MaxLength(5000)
  content = '';
}
```

각 데코레이터는 서로 다른 역할을 담당합니다.

| 데코레이터 | 역할 |
| --- | --- |
| `@FromBody()` | 같은 이름의 JSON 필드를 바인딩합니다. |
| `@IsDefined()` | `null`과 `undefined`를 거부합니다. 일반 문자열·길이 검증만으로 필수 값 조건이 생기지는 않습니다. |
| `@IsString()` | 다른 타입의 값을 거부합니다. 숫자를 문자열로 암묵적으로 변환하지 않습니다. |
| `@MinLength(...)` / `@MaxLength(...)` | 문자열 길이를 제한합니다. title은 3–120, content는 1–5000입니다. |

데코레이터가 붙은 필드는 예시처럼 초기화하세요. `title!: string`으로 바꾸지 마세요. 기본 표준 데코레이터 변환은 데코레이터가 붙은 필드의 해당 definite-assignment 형태를 지원하지 않습니다.

이 규칙은 공백을 제거하거나 HTML을 정제하지 않습니다. API는 허용된 문자열을 입력 그대로 저장합니다.

## 2. 기존 서비스에 생성 기능 추가하기

목록과 조회 메서드를 유지하면서 서비스 전체를 교체합니다.

{/* fluo-tutorial-source: examples/fluo-blog/03-validation-errors/src/posts.service.ts */}
```ts title="00-start/src/posts.service.ts"
import { NotFoundException } from '@fluojs/http';

import type { Post } from './post';

export class PostsService {
  // This mutable collection belongs to one application instance, not a database.
  private readonly posts: Post[] = [
    { id: '1', title: 'Hello, Fluo!', content: 'My first post.' },
  ];

  list(): readonly Post[] {
    return [...this.posts];
  }

  get(id: string): Post {
    const post = this.posts.find((candidate) => candidate.id === id);
    if (!post) {
      throw new NotFoundException(`Post ${id} was not found.`);
    }
    return post;
  }

  create(title: string, content: string): Post {
    const post: Post = { id: String(this.posts.length + 1), title, content };
    this.posts.push(post);
    return post;
  }
}
```

서비스가 ID를 정한 뒤 같은 애플리케이션 인스턴스의 이후 요청에서 사용할 게시글을 보관합니다. 이 단순한 순번은 학습용이며 영속적이거나 분산된 ID 전략은 아닙니다.

## 3. POST 라우트에 DTO 연결하기

{/* fluo-tutorial-source: examples/fluo-blog/03-validation-errors/src/posts.controller.ts */}
```ts title="00-start/src/posts.controller.ts"
import { Inject } from '@fluojs/core';
import { Controller, Get, HttpCode, Post as PostRoute, RequestDto } from '@fluojs/http';

import { CreatePostDto } from './create-post.dto';
import type { Post } from './post';
import { PostParamsDto } from './post-params.dto';
import { PostsService } from './posts.service';

@Inject(PostsService)
@Controller('/posts')
export class PostsController {
  constructor(private readonly posts: PostsService) {}

  @Get()
  list(): readonly Post[] {
    return this.posts.list();
  }

  @Get('/:id')
  @RequestDto(PostParamsDto)
  get(input: PostParamsDto): Post {
    return this.posts.get(input.id);
  }

  @PostRoute()
  @HttpCode(201)
  @RequestDto(CreatePostDto)
  create(input: CreatePostDto): Post {
    return this.posts.create(input.title, input.content);
  }
}
```

`Post as PostRoute`는 라우트 데코레이터와 `Post` 응답 인터페이스를 구분합니다. `@HttpCode(201)`은 생성 성공 상태를 명시합니다.

**검증이 실제로 연결되는 지점입니다.** `@RequestDto(CreatePostDto)`가 런타임 DTO를 선택하고 `@FromBody()`가 필드를 바인딩하며, 기본 HTTP 파이프라인은 `create`를 호출하기 전에 검증 규칙을 실행합니다. 예제의 Fastify bootstrap은 이미 이 파이프라인을 사용합니다. NestJS 방식의 전역 validation pipe를 설치하거나 컨트롤러에서 `DefaultValidator`를 직접 호출할 필요가 없습니다.

기능의 컨트롤러와 provider 등록을 유지합니다.

{/* fluo-tutorial-source: examples/fluo-blog/03-validation-errors/src/posts.module.ts */}
```ts title="00-start/src/posts.module.ts"
import { Module } from '@fluojs/core';

import { PostsController } from './posts.controller';
import { PostsService } from './posts.service';

@Module({
  controllers: [PostsController],
  providers: [PostsService],
})
export class PostsModule {}
```

루트 애플리케이션은 계속 이 기능을 import합니다.

{/* fluo-tutorial-source: examples/fluo-blog/03-validation-errors/src/app.ts */}
```ts title="00-start/src/app.ts"
import { Module } from '@fluojs/core';
import { HealthModule } from '@fluojs/runtime';

import { PostsModule } from './posts.module';

@Module({
  imports: [HealthModule.forRoot(), PostsModule],
})
export class AppModule {}
```

## 4. 잘못된 요청부터 거부하기

이전 서버를 종료하고 저장소 루트에서 실행합니다.

```bash
pnpm --filter @fluojs/example-fluo-blog build:00
pnpm --filter @fluojs/example-fluo-blog start:00
```

두 번째 터미널에서 너무 짧은 제목을 보냅니다.

```bash
curl -i -X POST http://127.0.0.1:3000/posts \
  -H 'content-type: application/json' \
  --data '{"title":"ab","content":"Valid content"}'
```

예상 상태 코드는 `400`입니다. 오류 본문은 다음과 같습니다.

```json
{
  "error": {
    "code": "BAD_REQUEST",
    "message": "Validation failed.",
    "status": 400,
    "details": [
      {
        "code": "MIN_LENGTH",
        "field": "title",
        "message": "title must have length at least 3.",
        "source": "body"
      }
    ]
  }
}
```

`error.requestId`가 추가될 수도 있습니다. `source`, `field`, `code`로 잘못된 입력을 식별할 수 있습니다. 클라이언트는 사람이 읽는 메시지를 파싱하지 않아야 합니다.

거부된 요청이 목록을 바꾸지 않았는지 확인합니다.

```bash
curl -i http://127.0.0.1:3000/posts
```

예상 결과는 `200`과 초기 게시글만 담은 배열입니다.

```json
[{"id":"1","title":"Hello, Fluo!","content":"My first post."}]
```

## 5. 생성한 게시글을 그대로 조회하기

서버를 재시작하지 않고 실행합니다.

```bash
curl -i -X POST http://127.0.0.1:3000/posts \
  -H 'content-type: application/json' \
  --data '{"title":"Learning Fluo","content":"Explicit modules and DI."}'
curl -i http://127.0.0.1:3000/posts/2
curl -i http://127.0.0.1:3000/posts
```

POST는 `201`, `/posts/2`는 `200`을 반환합니다. 두 본문은 동일합니다.

```json
{"id":"2","title":"Learning Fluo","content":"Explicit modules and DI."}
```

목록은 `200`과 두 게시글을 반환합니다.

```json
[
  {"id":"1","title":"Hello, Fluo!","content":"My first post."},
  {"id":"2","title":"Learning Fluo","content":"Explicit modules and DI."}
]
```

이 ID는 새 서버에서 성공한 POST를 정확히 한 번 실행했을 때의 결과입니다. POST를 반복하면 다음 ID로 다른 게시글이 생성됩니다.

## 6. 잘못된 입력과 없는 리소스 구분하기

```bash
curl -i http://127.0.0.1:3000/posts/999
curl -i http://127.0.0.1:3000/health
```

첫 요청은 `404`와 `{"error":{"code":"NOT_FOUND","message":"Post 999 was not found.","status":404}}`를 반환하며 `error.requestId`가 추가될 수 있습니다. 두 번째 요청은 계속 `200`과 `{"status":"ok"}`를 반환합니다.

`400`은 요청이 입력 계약을 만족하지 못했다는 뜻입니다. 여기서 `404`는 요청한 게시글이 없다는 뜻입니다. 둘을 오류 문자열이 담긴 성공 응답으로 바꾸지 마세요.

지금 기존 회귀 테스트를 실행합니다. 다음 수업에서 같은 요청 테스트 파일을 생성과 검증 사례까지 포함한 코드로 교체합니다.

```bash
pnpm --filter @fluojs/example-fluo-blog exec vitest run 00-start
```

기존 health, 목록, 조회, 없는 리소스 테스트가 계속 통과해야 합니다. 위 curl 명령으로 새 입력 경계를 확인했으며 다음 수업에서 이를 요청 테스트로 반복 검증하도록 만듭니다.
