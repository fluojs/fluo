Fluo is a TypeScript backend framework for applications that benefit from modules,
controllers and dependency injection. It connects these building blocks to HTTP
servers, databases and background work without relying on TypeScript's legacy
decorator metadata.

Start with a small application, then add the capabilities you need. You do not
need to install every Fluo package or understand its internals before writing
your first endpoint.

**New to Fluo?** [Create your first application](/docs/getting-started/quick-start),
then follow the Overview chapters with the same project. The recommended path
uses Node.js `>=24.0.0 <27`, TypeScript and Fastify.

## Why fluo?

Most decorator-heavy TypeScript frameworks depend on legacy compiler behavior. fluo keeps the programming model close to the JavaScript language path: no `experimentalDecorators`, no `emitDecoratorMetadata`, and no hidden reflection requirement.

Dependencies are explicit: a provider declares the tokens it needs, and a module
declares which providers and controllers belong together. This makes application
assembly visible in the code and lets tests replace dependencies deliberately.

Fluo is a good fit when an application needs a shared structure across several
features, testable services and clearly owned startup and shutdown work. If you
only need a single stateless handler, consider whether modules and dependency
injection add enough value for that application.

## How an application fits together

An HTTP application has four main pieces:

| Piece | Responsibility | Example |
| --- | --- | --- |
| Controller | Connect an incoming request to application work | A posts endpoint |
| Provider | Implement reusable behavior and dependencies | A posts service |
| Module | Register and expose related pieces | A posts feature module |
| Adapter | Connect the application to its host | A Fastify listener |

A request enters through the adapter and is dispatched to a controller. The
controller delegates business work to injected providers. Modules determine
which providers are available; they are not request handlers themselves.

The runtime assembles this graph before the application starts serving requests.
For a listener-based application, the standard entry point is
`FluoFactory.create(AppModule, { adapter })`, followed by `app.listen()`.
The [Getting started guide](/docs/getting-started/quick-start) generates a
complete entry point, including logging and host shutdown registration, so you
do not have to assemble those prerequisites from isolated fragments.

## Choose a platform deliberately

For a first local application, use Node.js and the Fastify adapter from Getting
started. Other adapters support different hosting models, including Bun, Deno
and Cloudflare Workers. A runtime adapter does not make every database driver,
transport or Node-specific package portable.

Check the [runtime adapter guide](/docs/guides/runtime-adapters) before moving
an application between hosts. In particular, a host-owned request handler has
different startup and shutdown responsibilities from a process-owned listener.
The supported package combinations matter as much as the language runtime.
